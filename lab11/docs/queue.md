# Очередь фоновых задач: устройство и обоснование

## 1. Что выносим в фон, а что нет

| Операция | В фон? | Почему |
|----------|:------:|--------|
| Уведомление о смене статуса | да | пользователю не нужно ждать отправки; если письмо не ушло, его можно повторить |
| Построение отчёта в файл | да | долгая операция; результат нужен не сразу, а «когда будет готов» |
| Проверка пароля при входе | нет | ответ нужен сейчас, без него нельзя продолжить |
| Создание задачи в базе | нет | пользователь должен видеть результат своего действия сразу |

Правило: в фон выносят то, что **долгое**, **может сломаться из-за внешнего сервиса** или **не обязано быть готово к моменту ответа**.

## 2. Устройство очереди в Redis

| Ключ | Тип | Назначение | Команды |
|------|-----|-----------|---------|
| `taskapp:queue:default` | список | ожидающие задачи | `LPUSH` (положить), `BLMOVE` (взять) |
| `taskapp:queue:default:processing` | список | задачи в работе | `BLMOVE` (сюда), `LREM` (убрать после ack) |
| `taskapp:queue:default:delayed` | отсортированное множество | ждут повтора | `ZADD` (отложить), `ZRANGEBYSCORE` + `ZREM` (вернуть) |
| `taskapp:queue:default:dead` | список | не выполнены за все попытки | `LPUSH`, `LRANGE` |

Посмотреть вручную:

```bash
redis-cli LLEN taskapp:queue:default
redis-cli LRANGE taskapp:queue:default 0 -1
redis-cli ZRANGE taskapp:queue:default:delayed 0 -1 WITHSCORES
```

## 3. Путь одной задачи

1. Обработчик запроса вызывает `Jobs::dispatch(тип, данные)` → `Queue::push` кладёт JSON-строку в `queue:default` и возвращает номер задачи. Ответ пользователю уходит сразу.
2. Воркер вызывает `Queue::reserve`: `BLMOVE` перекладывает самую старую задачу из `queue:default` в `queue:default:processing` (если очередь пуста, ждёт до 2 секунд).
3. Воркер вызывает `Jobs::run`: по типу задачи выбирается класс (`NotificationJob`, `ReportJob`), вызывается его `handle()`.
4. Успех: `Queue::ack` удаляет задачу из «в работе».
5. Ошибка (исключение): `Queue::fail` увеличивает счётчик попыток. Попыток меньше трёх: задача уходит в `delayed` с паузой 2, 4, 8 секунд, потом `Queue::promote` возвращает её в очередь. Попытки кончились: задача уходит в `dead` вместе с текстом ошибки.

В `Queue::fail` задача сначала кладётся в новое место (`delayed` или `dead`) и только потом удаляется из «в работе». Если процесс упадёт между этими двумя шагами, задача окажется в двух списках (будет выполнена дважды), но не пропадёт.

## 4. Гарантии доставки

| Что случилось | Что с задачей | Почему |
|---------------|---------------|--------|
| обработчик бросил исключение | повтор, затем «мёртвая» очередь | `Queue::fail` |
| воркер убит (`kill -9`) во время работы | остаётся в «в работе», при запуске возвращается в очередь | `Queue::recover` |
| воркер остановлен Ctrl+C | текущая задача доделывается | обработка `SIGINT`/`SIGTERM` |
| Redis недоступен в момент постановки | **задача потеряна**: `Jobs::dispatch` вернёт `null`, операция пользователя уже выполнена | в этой работе уведомление не критично; для важных задач нужен outbox (см. раздел 6) |

Очередь даёт гарантию «**как минимум один раз**» (at-least-once): задача выполнится хотя бы раз, но после сбоя может выполниться два раза. Гарантии «ровно один раз» очередь не даёт; её обеспечивают обработчики.

## 5. Идемпотентность

Задача `notification` может быть выполнена повторно (воркер успел записать уведомление, но не успел подтвердить). Чтобы повтор был безопасным, в таблице `notifications`:

```sql
UNIQUE (job_id, user_id)
...
INSERT INTO notifications (job_id, user_id, task_id, message) VALUES (...)
ON CONFLICT (job_id, user_id) DO NOTHING
```

Повторная задача с тем же `job_id` не создаёт второго уведомления. Проверка есть в автотестах (раздел 11).

Задача `report` идемпотентна по своей природе: повтор перезаписывает тот же файл `report-<номер>.csv` и ставит ту же заявку в `done`.

## 6. Ограничения учебной реализации

- **Потеря при недоступном Redis.** Если Redis не отвечает в момент `dispatch`, задача теряется. В рабочих системах для важных операций используют схему **outbox**: задачу записывают в таблицу базы в той же транзакции, что и сама операция, а отдельный процесс переносит её в очередь.
- **`recover` рассчитан на один воркер.** При запуске он возвращает в очередь *все* задачи из «в работе», в том числе те, которые прямо сейчас выполняет другой живой воркер. В рабочих системах задачам задают срок выполнения (визибилити-таймаут) и возвращают только просроченные.
- **Одна очередь.** Отчёт, поставленный после десяти уведомлений, ждёт, пока воркер выполнит все десять (на замере отчёт ждал 8 секунд). Лечится отдельными очередями и отдельными воркерами для долгих задач (`--queue=reports`).
- **Нет приоритетов и расписания.** Только порядок поступления и пауза перед повтором.
- **Запуск воркера вручную.** В рабочей системе воркером управляет Supervisor или systemd (перезапуск при падении, несколько копий), в Docker — отдельный контейнер.

## 7. Чем ещё можно было сделать очередь

| Способ | Плюсы | Минусы |
|--------|-------|--------|
| PostgreSQL: таблица `jobs` + `SELECT ... FOR UPDATE SKIP LOCKED` | не нужен новый компонент; задача и данные в одной транзакции | нагрузка на основную базу, нет блокирующего ожидания |
| Redis-список с `LPUSH` + `BRPOP` | проще всего | задача пропадает, если воркер упал после `BRPOP` |
| Redis Streams | группы потребителей, подтверждения, история | сложнее для начинающих |
| Gearman | готовый сервер очереди и воркеров | отдельный сервис, меньше сообщество |
| RabbitMQ, Kafka | гарантии, маршрутизация, масштаб | тяжёлая инфраструктура; для учебной системы избыточно |
