# Сравнение производительности: без кеша и с кешем

## Методика

**Стенд.** Apple M3 (8 ядер, 16 ГБ), macOS 15.6; PHP 8.2.33 (встроенный сервер `php -S` на 4 процессах, `PHP_CLI_SERVER_WORKERS=4`), расширение phpredis 6.3.0; PostgreSQL 16 и Redis 7.4 в Docker на том же компьютере; клиент измерений `bin/benchmark.php` на том же компьютере.

**Данные.** `php bin/load-bigdata.php`: 49 дополнительных проектов (всего 52) и 500 000 дополнительных задач (всего 500 007; `sql/bigdata.sql`, воспроизводимо: `setseed(0.42)`).

**Запуск.**

```bash
PHP_CLI_SERVER_WORKERS=4 php -S localhost:8000 -t public
php bin/benchmark.php --n=60 --c=8 --d=3
```

**Что измеряется** для каждого сценария (`bin/benchmark.php`):

1. **Без кеша:** 60 запросов подряд с заголовком `X-Cache-Mode: off` (кеш обходится, каждый запрос идёт в базу).
2. **С кешем:** кеш приложения очищается, затем 60 запросов подряд. Первый — «холодный» (MISS: чтение из базы и запись в Redis), остальные 59 — «тёплые» (HIT). Скрипт проверяет по заголовку `X-Cache`, что первый запрос был MISS, а остальные HIT.
3. **Пропускная способность:** нагрузка в течение 3 секунд, всё время идут 8 одновременных запросов (`curl_multi`), отдельно без кеша и с тёплым кешем; результат — сколько запросов в секунду обработал сервер. Перед измерением каждого сценария выполняется прогрев (3 запроса не учитываются).

Время измеряется на стороне клиента (от отправки запроса до получения всего ответа, `hrtime`). В каждый запрос входят накладные расходы, которые кеш не ускоряет: запуск PHP, проверка токена (два запроса к базе), формирование ответа.

## Повторяемость

Измерение выполнено три раза (первые два запуска сделаны до того, как параллельная нагрузка стала фиксированной по времени, поэтому сравниваем только ускорение по последовательным запросам):

| Сценарий | Запуск 1 (40 запросов) | Запуск 2 (60 запросов) | Запуск 3 (60 запросов, таблица выше) |
|----------|-----------------------:|-----------------------:|-------------------------------------:|
| Список проектов | ×1,1 | ×2,0 | ×1,1 |
| Карточка задачи | ×0,9 | ×0,9 | ×0,9 |
| Список задач (последние 100) | ×2,9 | ×2,8 | ×2,8 |
| Поиск по названию | ×30,4 | ×44,8 | ×43,5 |
| Отчёт по проектам | ×15,2 | ×17,3 | ×16,5 |
| Задачи проекта 7, в работе | ×2,1 | ×2,3 | ×2,1 |
| Задачи, сортировка по названию | ×38,8 | ×45,3 | ×34,3 |

Абсолютные миллисекунды «без кеша» колебались заметно (например, поиск: 250, 409, 312 мс), потому что база и сервер работают на одном компьютере вместе с остальными программами. Но **выводы одинаковы во всех запусках**: тяжёлые запросы ускоряются в десятки раз, лёгкие — нет, карточка по номеру с кешем чуть медленнее (×0,9).

## Анализ

1. **Выигрыш определяется стоимостью исходного запроса.** Поиск по названию (312 мс), сортировка по названию, отчёт (115 мс) читают всю таблицу из полумиллиона строк. С кешем они отвечают за 7,2 мс. Ускорение — от ×16,5 до ×43,5, пропускная способность выросла примерно с единиц–десятков до сотен запросов в секунду.
2. **Дешёвые запросы почти не выигрывают.** Карточка задачи (×0,9) и список проектов (×1,1): PostgreSQL читает строку по первичному ключу или маленькую таблицу за доли миллисекунды, а Redis, как и база, живёт на том же компьютере, и обращение к нему тоже занимает время. Весь ответ — это в основном накладные расходы запроса. Вывод: перед внедрением кеша нужно измерять, а не угадывать.
3. **Пол времени ответа.** При HIT время ответа у всех сценариев схоже: около 7,2 мс. Это стоимость запуска PHP, проверки токена и ответа. Чтобы опуститься ниже, нужно кешировать уже само «получение пользователя по токену» (задание повышенной сложности) или использовать постоянно работающий PHP (PHP-FPM, RoadRunner).
4. **Холодный кеш.** Первый запрос с пустым кешем (MISS) не быстрее запроса без кеша (112 мс против 115 мс у отчёта): работа та же, плюс запись в Redis. Выигрыш виден со второго запроса. После очистки кеша, перезапуска Redis или массовой инвалидации приложение временно работает как без кеша.
5. **Зависимость от доли попаданий.** В измерении все повторные запросы одинаковы, поэтому доля попаданий 100%. В реальной системе она ниже: запросы разнообразны (разные поисковые слова), данные меняются и инвалидируются. Если данные меняются очень часто, большая часть запросов становится промахами, и кеш даёт мало. Если запросов слишком много разных (каждый поиск уникален), кеш наполняется записями, которые больше никто не прочитает.
6. **Кеш эффективнее всего** для дорогих запросов (агрегаты, поиск по подстроке, сортировка больших таблиц), которые часто повторяются и допускают небольшое отставание данных: отчёты, справочники, популярные списки.

## Ограничения измерения

- Всё работает на одном компьютере: сеть между приложением, PostgreSQL и Redis почти не вносит задержки; в реальной системе обращение к Redis стоит дороже (но база по сети тоже).
- Встроенный сервер PHP с 4 процессами не заменяет PHP-FPM + nginx; абсолютные цифры другого сервера будут иными, а соотношения похожими.
- При повторном запуске цифры слегка меняются (±10–20%): запускайте измерение несколько раз и сравнивайте соотношения, а не отдельные миллисекунды.
- PostgreSQL кеширует страницы таблиц сам (общий буфер и кеш операционной системы): «без кеша» в нашем смысле означает «без кеша приложения», база при этом работает на тёплых данных. Для «холодной» базы разница была бы ещё больше.
