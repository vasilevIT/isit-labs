# Описание механизма кеширования

## Выбор данных для кеша

Критерии: как часто читают, как часто меняют, сколько стоит получить из базы, допустимо ли показывать копию, которая отстаёт от базы на время жизни записи.

| Данные | Читают | Меняют | Стоимость в базе | «Чуть устаревшее» допустимо? | Решение |
|--------|--------|--------|------------------|------------------------------|---------|
| список проектов | на каждой странице | редко | малая, но запросов очень много | да, плюс инвалидация | кешируем, TTL 300 с |
| карточка задачи | при открытии задачи | при редактировании | очень малая (строка по ключу) | да, плюс инвалидация | кешируем, TTL 60 с (выигрыш небольшой, см. измерения) |
| список задач с параметрами | постоянно | при каждом изменении задач | заметная: сортировка, `COUNT`, поиск `ILIKE` | да, плюс инвалидация версией | кешируем, TTL 60 с |
| отчёт по проектам | руководитель открывает часто | при любом изменении задач | большая: `GROUP BY` по всей таблице | да, плюс инвалидация | кешируем, TTL 120 с |
| данные входа (токены, пароли) | при каждом запросе | при входе и выходе | малая | **нет**: отозванный токен не должен работать из кеша | не кешируем |
| результат создания, изменения, удаления | — | — | — | — | не кешируем: запись всегда идёт в базу |

## Ключи и время жизни

| Ключ | Что хранит | TTL | Комментарий |
|------|------------|-----|-------------|
| `projects:all` | массив всех проектов | 300 с | справочник; страховка на случай пропущенной инвалидации |
| `tasks:item:{id}` | одна задача | 60 с | номер в ключе: у каждой задачи своя запись |
| `tasks:list:v{N}:{md5}` | `{rows: [...], total: N}` для одного набора параметров | 60 с | в ключ входят все параметры: статус, проект, поиск, сортировка, `limit`, `offset`; `N` — номер версии |
| `tasks:version` | счётчик версии списков | нет | растёт на 1 при любом изменении задач (`INCR`) |
| `report:summary` | сводка по проектам | 120 с | не зависит от параметров |

Все ключи в Redis начинаются с префикса `taskapp:` (его добавляет phpredis: параметр `Redis::OPT_PREFIX`).

## Инвалидация

| Событие | Что делается | Почему |
|---------|--------------|--------|
| создана задача | версия `tasks:version` +1; удалён `report:summary` | новая задача может попасть в любой список и меняет отчёт |
| изменена задача | то же; удалён `tasks:item:{id}` | устарела и карточка |
| удалена задача | то же; удалён `tasks:item:{id}` | не должна отдаваться из кеша |
| создан, изменён, удалён проект | удалены `projects:all` и `report:summary` | в отчёте названия проектов |
| истёк TTL | Redis удаляет ключ сам | страховка |

Для списков применена **версия набора ключей**: вариантов запроса бесконечно много, перечислить и удалить их нельзя. Вместо удаления номер версии увеличивается, новые запросы ищут ключи с новой версией (промах, данные берутся из базы), а старые ключи Redis удалит сам по истечении TTL. Цена: до истечения TTL в Redis лежат ненужные ключи старых версий.

## Устойчивость

- подключение к Redis с таймаутом 0,5 с; любые `RedisException` перехватываются;
- после первой неудачи в запросе повторных обращений к Redis нет;
- при недоступном Redis ответ формируется из базы (`X-Cache: BYPASS`), приложение не падает; проверено остановкой контейнера Redis;
- `CACHE_ENABLED=0` отключает кеш целиком.

## Что изменилось в API

| Изменение | Описание |
|-----------|----------|
| `GET /api/tasks`: параметры `limit` (по умолчанию 100, не больше 500) и `offset` | на 500 тысячах задач ответ «все задачи» невозможен; общее число — в заголовке `X-Total-Count` |
| `GET /api/reports/summary` | сводка по проектам: всего задач, по статусам, просроченные |
| заголовок ответа `X-Cache` | `HIT`, `MISS` или `BYPASS` |
| заголовок запроса `X-Cache-Mode: off` | обойти кеш для этого запроса (только при `debug = true`): режим измерений |

## Что проверено

Автотесты (`tests/api-tests.php`, разделы 8 и 9): первый запрос — MISS, второй — HIT; данные из кеша совпадают с данными из базы; у ключей есть TTL; кеш не отменяет проверку входа; после `PATCH`, `POST`, `DELETE` данные свежие; разные параметры списка — разные ключи; отчёт пересчитывается после изменений; обход кеша заголовком; после истечения TTL запрос снова MISS. Заодно регрессионные проверки лабораторной работы №9 подтверждают, что кеш нигде не показывает устаревшее.
