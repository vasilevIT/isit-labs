Цель лабораторной работы

Изучить основы разработки клиентской части веб-приложений, реализовать обработку пользовательских событий, взаимодействие с сервером посредством асинхронных запросов и динамическое изменение содержимого веб-страницы с использованием JavaScript.

Опыт программирования на JavaScript не требуется: в работе есть готовая заготовка, подробные комментарии и шпаргалка по синтаксису.

Постановка задачи

На основе ранее разработанных макетов пользовательского интерфейса необходимо реализовать клиентскую логику информационной системы.

В ходе работы требуется:

  • реализовать обработку пользовательских событий;
  • выполнить изменение содержимого страницы средствами JavaScript;
  • реализовать взаимодействие с сервером с использованием асинхронных запросов;
  • обеспечить обновление интерфейса без перезагрузки страницы.

Источник данных. Серверной части пока нет, и писать её не нужно. В качестве источника данных используется учебный сервер (mock API), который работает прямо в браузере. Он состоит из двух файлов:

  • js/mock-api.js — «движок», который принимает запросы fetch и находит ответ в таблице. Его менять не нужно.

Код запросов в вашей программе будет таким же, как для настоящего сервера. Когда в следующих работах появится backend, менять придётся только адреса.

Теоретическая база

1. Что такое клиентская логика

Клиентская логика — это программа на JavaScript, которая работает в браузере пользователя. Любое действие на странице устроено по одной схеме: событие → действие → результат на странице. Например: пользователь нажал «Удалить» → программа удалила строку из таблицы → счётчик задач уменьшился.

Помните из лекции: браузерному коду доверять нельзя, его можно изменить. Поэтому проверки в браузере нужны для удобства пользователя, а окончательную проверку выполняет сервер.

3. События

Событие — сигнал о том, что на странице что-то произошло. Мы говорим браузеру: «когда произойдёт это событие у этого элемента — вызови эту функцию».

function onFormSubmit(event) { event.preventDefault(); // отменить стандартное поведение: перезагрузку страницы console.log('Форма отправлена'); } const form = document.getElementById('task-form'); // найти элемент по id form.addEventListener('submit', onFormSubmit); // событие, функция (без скобок!)

Без event.preventDefault() браузер при отправке формы перезагрузит страницу, и введённые данные пропадут. Это самая частая ошибка новичков.

4. DOM: изменение содержимого страницы

DOM — это «живая» модель страницы: каждый тег превращается в объект, которым можно управлять из JavaScript. Все изменения тут же видны пользователю, страница при этом не перезагружается.

Безопасность. Текст, введённый пользователем, нужно записывать через textContent, а не через innerHTML. Свойство innerHTML разбирает текст как HTML-код, и злоумышленник сможет внедрить вредоносный скрипт (XSS-атака). textContent всегда вставляет только текст.

5. Асинхронные запросы: fetch

Запрос к серверу занимает время (десятки и сотни миллисекунд). Если бы страница ждала ответа «стоя на месте», она бы «зависла». Поэтому запросы выполняются асинхронно: страница продолжает работать, а когда ответ пришёл, программа идёт дальше.

Для этого используют два слова: async перед функцией, которая отправляет запрос, и await перед действием, результата которого нужно дождаться. Правило запомнить просто: перед fetch и перед вызовом функции, которая его использует, ставьте await, а функцию, где встретился await, объявляйте с async.

async function loadTasks() { const response = await fetch('/api/tasks'); // 1. отправили запрос и дождались ответа if (!response.ok) { // 2. fetch НЕ считает ошибкой коды 404 и 500! throw new Error('Ошибка сервера: ' + response.status); } return await response.json(); // 3. достали данные из ответа } async function showTasks() { try { const tasks = await loadTasks(); // выполнится, если всё хорошо console.log(tasks); } catch (error) { // выполнится, если где-то выше случилась ошибка console.log('Не получилось:', error.message); } finally { console.log('Это выполнится в любом случае'); } }

Частая ошибка: забыть await. Вместо данных вы получите объект Promise, и в консоли увидите Promise { <pending> }.

8. Учебный сервер: какой запрос — какие данные

Откройте файл js/mock-data.js. В нём две части. Первая — данные: несколько массивов с записями, как таблицы в базе данных.

const tasks = [ { id: 1, title: 'Сверстать главную страницу', status: 'done', priority: 'high' }, { id: 2, title: 'Подключить форму обратной связи', status: 'in_progress', priority: 'medium' }, // ... ещё записи ]; const users = [ { id: 1, name: 'Анна Петрова', role: 'Руководитель' }, ];

Вторая часть — таблица ROUTES: слева запрос (метод и адрес), справа функция, которая возвращает ответ.

const ROUTES = { 'GET /api/tasks': function (query) { return filterList(tasks, query); // выбрать записи по параметрам из адреса }, 'GET /api/users': function () { return users; // отдать весь массив } };

Читается так: «когда страница отправит запрос GET /api/tasks, сервер вернёт массив tasks, отфильтрованный по параметрам из адреса». Вот что страница получает на разные запросы:

ЗапросЧто вернёт сервер
GET /api/tasks200 и массив всех задач
GET /api/tasks?status=done200 и массив задач со статусом done (фильтр работает по любому полю)
GET /api/tasks?q=форма200 и массив задач, в тексте которых есть слово «форма» (поиск по всем текстовым полям)
GET /api/tasks?status=done&q=форма200 и задачи, подходящие под оба условия
GET /api/tasks?status=&q=пустые значения означают «без фильтра»: все задачи
GET /api/users200 и массив всех пользователей
любой запрос, которого нет в ROUTES404 и сообщение, какой строки не хватает

Параметр query — объект с параметрами из адреса: для запроса /api/tasks?status=done&q=форма он равен { status: 'done', q: 'форма' }. Функцию filterList писать не нужно: она уже есть в mock-api.js и выбирает из массива подходящие записи.

Как приспособить сервер под свою предметную область (Шаг 1): замените массив tasks своим массивом (например, orders), переименуйте адрес в ROUTES ('GET /api/orders') и поменяйте тот же адрес в функции loadTasks() в app.js. Если у вас несколько сущностей, добавьте массив и строку в ROUTES для каждой: users в заготовке — пример второй сущности.

Для проверки страницы «в плохих условиях» в консоли браузера доступны команды:

MockApi.setDelay(2000, 3000) // медленный сервер: ответ придёт через 2–3 секунды MockApi.setErrorRate(1) // все запросы будут отвечать ошибкой 500 MockApi.setNetworkDown(true) // «пропал интернет»: запрос завершится ошибкой сети // вернуть нормальный режим: MockApi.setDelay(300, 800); MockApi.setErrorRate(0); MockApi.setNetworkDown(false)

Для заданий повышенной сложности внизу ROUTES есть готовые строки (сейчас закомментированы) для запросов GET /api/tasks/5, POST /api/tasks и DELETE /api/tasks/5. Чтобы включить их, уберите // в начале строк. Созданные и удалённые записи хранятся до перезагрузки страницы.

Повышенная сложность (по желанию)

  • отправка новой задачи на сервер: включите строку POST /api/tasks в ROUTES и отправьте fetch с method: 'POST' и телом запроса — объектом задачи (задача сохраняется до перезагрузки страницы);
  • удаление на сервере: включите строку DELETE /api/tasks/:id в ROUTES и отправьте запрос при нажатии «Удалить»;
  • показ ошибки сервера (код 422) рядом с полем формы;
  • защита от «гонки запросов»: если пользователь быстро меняет фильтр, показывать только ответ на последний запрос;
  • задержка перед поиском: отправлять запрос не на каждую букву, а через 300 мс после последнего нажатия (setTimeout, clearTimeout).

Пример запроса на создание (после включения строки POST /api/tasks в ROUTES):

async function createTask(title, priority) { const response = await fetch('/api/tasks', { method: 'POST', // метод запроса headers: { 'Content-Type': 'application/json' }, // сообщаем, что тело — JSON body: JSON.stringify({ title: title, priority: priority }) // объект -> строка JSON }); if (!response.ok) { throw new Error('Ошибка сервера: ' + response.status); // 422, если не введено название } return await response.json(); // сервер вернёт созданную задачу }

Требования к оформлению

Результаты лабораторной работы должны быть оформлены в виде Git-репозитория. Рекомендуется делать отдельный коммит после каждого шага с понятным сообщением (например, «lab5: обработка событий»).

Рекомендуемая структура:

lab5/ ├── README.md ├── src/ ├── images/ └── docs/

Файл README.md должен содержать:

  • название лабораторной работы;
  • цель работы;
  • описание реализованной клиентской логики;
  • описание обработки пользовательских событий;
  • описание работы с DOM и асинхронными запросами;
  • вывод.

При необходимости в репозиторий добавляются:

  • исходный код (src/);
  • изображения интерфейса (images/);
  • дополнительные материалы (docs/), например, результаты проверки по Шагу 5.

При оформлении рекомендуется:

  • использовать язык разметки Markdown;
  • применять заголовки, списки и таблицы;
  • сопровождать основные этапы реализации пояснениями;
  • придерживаться понятной структуры каталогов и файлов.
