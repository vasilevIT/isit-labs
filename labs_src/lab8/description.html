Теоретическая база

1. Из чего состоит база данных

Реляционная база данных похожа на файл Excel с несколькими листами. Отличие в том, что база понимает связи между листами, проверяет данные и позволяет работать с ней многим программам одновременно.

ТерминЧто это простыми словамиПример
Таблицанабор однотипных записей, описывает одну сущностьtasks — задачи
Строка (запись)один объектодна задача
Столбец (поле)свойство объекта; у каждого столбца свой типtitle, status, due_date
Первичный ключ (PK)столбец с уникальным номером строкиtasks.id
Внешний ключ (FK)столбец, хранящий номер строки другой таблицы: так создаётся связьtasks.project_id → projects.id
СУБДпрограмма, которая управляет базойPostgreSQL

Главное правило проектирования (нормализация): одни и те же данные не хранятся в нескольких местах. В каждой ячейке одно значение (не список через запятую); каждая таблица описывает одну сущность; повторяющиеся данные выносятся в отдельную таблицу и подключаются по ключу. Например, имя исполнителя хранится один раз в users, а в задаче только его номер assignee_id.

3. Ограничения целостности

Ограничения — правила, которые описываются один раз при создании таблицы и проверяются базой при каждой записи, из какой бы программы она ни пришла.

ОграничениеЧто означаетПример
PRIMARY KEYуникальный непустой номер строкиid SERIAL PRIMARY KEY
REFERENCESвнешний ключ: значение должно существовать в другой таблицеproject_id INTEGER REFERENCES projects (id)
NOT NULLполе обязательноtitle VARCHAR(200) NOT NULL
UNIQUEзначение не повторяетсяemail VARCHAR(255) UNIQUE
CHECKзначение удовлетворяет условиюCHECK (status IN ('new', 'in_progress', 'done'))
DEFAULTзначение по умолчаниюstatus VARCHAR(20) DEFAULT 'new'

Если запрос нарушает правило, PostgreSQL отказывается его выполнять и называет нарушенное ограничение:

INSERT INTO tasks (project_id, title) VALUES (99, 'Задача без проекта'); ERROR: insert or update on table "tasks" violates foreign key constraint "tasks_project_id_fkey" DETAIL: Key (project_id)=(99) is not present in table "projects".

5. ER-диаграмма

ER-диаграмма (Entity–Relationship, «сущность — связь») показывает таблицы, их поля и связи. Мы рисуем её в PlantUML, как диаграммы в лабораторных работах №2–4: текстовый файл .puml хранится в Git, а картинка получается из него автоматически.

entity "projects" as projects { * id : SERIAL <<PK>> -- * title : VARCHAR(150) <<UNIQUE>> * owner_id : INTEGER <<FK>> } users ||--o{ projects : "1 : N" ' один участник — много проектов users ||--o| user_profiles : "1 : 1" tasks ||--o{ task_tags : "N : M" ' N:M рисуется через связующую таблицу

Значки на концах линии: || — ровно один, |o — ноль или один, o{ — ноль или много. Пример готовой диаграммы для системы управления задачами:

6. Как работать с PostgreSQL

С Docker. В папке с docker-compose.yml выполните docker compose up -d — запустится PostgreSQL 16 с пустой базой taskdb. Консоль: docker compose exec db psql -U postgres -d taskdb. Папка sql/ видна внутри контейнера как /sql, поэтому скрипт выполняется командой \i /sql/01_schema.sql.

Без Docker. Создайте базу (CREATE DATABASE taskdb;), подключитесь к ней (psql -U postgres -d taskdb) и выполняйте скрипты по пути на своём компьютере: \i sql/01_schema.sql (запускайте psql из папки lab8). В pgAdmin и DBeaver откройте файл в редакторе запросов (Query Tool / SQL Editor) и выполните его целиком.

Параметры подключения для pgAdmin и DBeaver: хост localhost, порт 5432, база taskdb, пользователь postgres, пароль secret (задан в docker-compose.yml).

7. CRUD-операции и REST API

Каждому методу REST API из лабораторной работы №7 соответствует команда SQL:

ОперацияREST APISQL
CreatePOST /api/tasksINSERT INTO tasks (title, project_id) VALUES ('...', 1) RETURNING id;
Read (список)GET /api/tasks?status=doneSELECT id, title FROM tasks WHERE status = 'done' ORDER BY due_date;
Read (одна)GET /api/tasks/5SELECT ... FROM tasks WHERE id = 5;
UpdatePATCH /api/tasks/5UPDATE tasks SET status = 'done' WHERE id = 5;
DeleteDELETE /api/tasks/5DELETE FROM tasks WHERE id = 5;

Три правила, которые спасают от самых частых ошибок:

  • UPDATE и DELETE всегда с WHERE. Без условия изменятся или удалятся все строки таблицы. Перед изменением выполните SELECT с тем же WHERE;
  • пустое значение проверяется через IS NULL, а не = NULL: сравнение с NULL знаком равенства никогда не даёт истину;
  • для необязательной связи нужен LEFT JOIN. Обычный JOIN оставляет только строки, у которых есть пара: задачи без исполнителя пропадут из результата.

8. Индексы и EXPLAIN ANALYZE

Индекс — вспомогательная структура, как алфавитный указатель в конце книги: вместо чтения всей таблицы база сразу находит нужные строки. PostgreSQL сам создаёт индексы только для PRIMARY KEY и UNIQUE. Для внешних ключей и столбцов из частых условий WHERE и ORDER BY индексы создаёте вы:

CREATE INDEX idx_tasks_project_id ON tasks (project_id); -- по одному столбцу CREATE INDEX idx_tasks_assignee_status ON tasks (assignee_id, status); -- составной, по двум

Как узнать, помог ли индекс. Команда EXPLAIN ANALYZE перед запросом выполняет его и показывает план — способ, которым база искала данные, — и фактическое время. План читается снизу вверх:

В планеЧто это значит
Seq Scan, Parallel Seq Scanполный перебор таблицы (на больших таблицах — медленно)
Rows Removed by Filterсколько строк прочитано зря
Index Scan, Bitmap Index Scanпоиск по индексу
Sortотдельная сортировка результата
Execution Timeобщее время выполнения в миллисекундах — его сравниваем «до» и «после»
EXPLAIN ANALYZE SELECT id, title FROM tasks WHERE project_id = 500; -- до индекса: Parallel Seq Scan on tasks ... Rows Removed by Filter: 166505 ... Execution Time: 14.899 ms -- после индекса: Bitmap Index Scan on idx_tasks_project_id ... Execution Time: 0.556 ms

На маленьких таблицах индексы не видны. На 7 задачах PostgreSQL всегда выберет перебор: прочитать одну страницу таблицы быстрее, чем обращаться к индексу. Поэтому для оптимизации в заготовке есть скрипт 05_test_data.sql, который за 10–30 секунд добавляет 500 000 задач.

У индекса есть цена: он занимает место на диске и замедляет INSERT, UPDATE и DELETE (базе нужно обновить и таблицу, и все её индексы). Индекс не помогает, если запрос читает большую часть таблицы или ищет подстроку LIKE '%слово%'. Поэтому индексы создают только для частых запросов и всегда проверяют EXPLAIN ANALYZE.

9. Как искать ошибки

  1. Читайте сообщение PostgreSQL целиком: в нём есть номер строки скрипта (psql:/sql/01_schema.sql:42), а в строке DETAIL — какое значение нарушило правило.
  2. relation "tasks" does not exist — таблицы нет: не выполнен 01_schema.sql, опечатка в имени или вы подключены не к той базе (\c taskdb).
  3. syntax error at or near ... — смотрите на слово, указанное в сообщении, и на строку перед ним: чаще всего пропущена запятая между столбцами или лишняя запятая после последнего столбца.
  4. current transaction is aborted — внутри BEGIN была ошибка; выполните ROLLBACK;.
  5. Приглашение psql сменилось на taskdb-# или taskdb'# — не закрыта команда (нет ;) или кавычка. Нажмите Ctrl+C.
  6. Порядок создания важен: таблица, на которую ссылаются (projects), должна быть создана раньше таблицы со ссылкой (tasks), а в DROP TABLE — наоборот.
