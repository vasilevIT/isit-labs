Теоретическая база

1. Что такое API и REST

API (Application Programming Interface) — это «меню» сервера: список запросов, которые программа-клиент может отправить, и ответов, которые получит. Сайт из лабораторной работы №6 тоже отвечает на запросы, но возвращает готовые HTML-страницы, а клиентскому приложению нужны чистые данные.

REST — набор соглашений о том, как строить такое «меню» поверх протокола HTTP. Главные идеи:

  • всё — ресурсы. Ресурс — это сущность системы (задачи, проекты, участники). У каждого ресурса есть адрес (URL);
  • действие задаётся HTTP-методом, а не словом в адресе: не /getTask, а GET /api/tasks/5;
  • сервер не помнит клиента между запросами: каждый запрос содержит всё необходимое;
  • данные передаются в JSON, а результат сообщается кодом ответа (200, 404, 422 и т. д.).

2. Ресурсы и адреса

Правила, по которым составляются адреса:

  • адрес — это существительное во множественном числе: /api/tasks, /api/projects. Глаголов в адресе нет;
  • номер записи добавляется через слэш: /api/tasks/5 — задача с номером 5;
  • связь «проект → его задачи» выражается вложенным адресом: /api/projects/2/tasks;
  • необязательные условия (фильтр, поиск) передаются после «?»: /api/tasks?status=done&project_id=1;
  • все адреса API начинаются с /api, чтобы их можно было отличить от страниц сайта.

PUT по правилам REST заменяет запись целиком, а PATCH меняет только присланные поля. Браузер из адресной строки умеет отправлять только GET, поэтому для остальных методов нужен Postman или curl.

4. Коды ответа

Клиент узнаёт результат запроса прежде всего по коду. В этой работе используются:

КодНазваниеКогда возвращать

201Createdзапись создана; в заголовке Location адрес новой записи
204No Contentзапись удалена; тела у ответа нет

Различие 400 и 422: {"title": — это не JSON вообще (400); {"title": "Да"} — JSON верный, но название слишком короткое (422).

5. Формат JSON

JSON — текстовый формат данных. Объект записывается в фигурных скобках, список — в квадратных, строки — только в двойных кавычках, после последнего элемента запятой нет:

{ "id": 8, "project_id": 1, "title": "Проверить API", "status": "new", "priority": "high", "due_date": null }

В PHP два действия: json_decode($text, true) превращает JSON в массив, json_encode($array) превращает массив в JSON. В заготовке это уже сделано внутри функций json_input() и json_response().

Единый формат ошибок облегчает жизнь клиенту: всегда один и тот же вид.

{ "error": "Ошибка проверки данных", "errors": { "title": "Название — не короче 3 символов", "status": "Статус: new, in_progress или done" } }

7. Проверка данных на сервере

Клиенту доверять нельзя: он может прислать что угодно. Поэтому перед сохранением каждое поле проверяется, а все найденные ошибки возвращаются сразу (код 422), чтобы клиент мог исправить их за один раз. В заготовке проверка уже написана в приватном методе validate() каждого контроллера: он возвращает массив поле => сообщение, пустой массив означает, что всё хорошо. Метод clean() оставляет только известные поля и отбрасывает лишнее (например, попытку изменить id).

8. Как отправлять и проверять запросы

Postman. Создайте запрос (New → HTTP), выберите метод, введите адрес вида http://localhost:8000/api/tasks. Для POST, PUT и PATCH откройте вкладку Body, выберите raw и тип JSON, введите тело запроса. Нажмите Send. В нижней части видны код ответа (Status), тело ответа и вкладка Headers (там Location, Allow).

curl (запасной вариант, работает в терминале):

curl -i http://localhost:8000/api/tasks/3 # GET: -i показывает код и заголовки curl -i -X POST http://localhost:8000/api/tasks -d '{"title":"Проверить API","project_id":1}' curl -i -X PATCH http://localhost:8000/api/tasks/3 -d '{"status":"done"}' curl -i -X DELETE http://localhost:8000/api/tasks/3

Данные настоящие. Запросы POST, PATCH и DELETE меняют файлы в storage/. Если вы удалили что-то лишнее, верните исходные данные: git checkout storage (при условии, что вы сделали коммит до экспериментов).

9. Как описывать API

Документация нужна тому, кто будет вызывать ваш API (например, автору клиентского приложения): он не читает ваш код. Для каждой конечной точки (endpoint) пишется одинаковый блок:

### POST /api/tasks — создать задачу Параметры тела (JSON): | Поле | Тип | Обязательное | Описание | |------------|--------|--------------|--------------------------------------------| | title | string | да | название, не короче 3 символов | | project_id | number | да | номер существующего проекта | | status | string | нет | new (по умолчанию), in_progress, done | Пример запроса: POST /api/tasks {"title": "Проверить API", "project_id": 1} Пример ответа (201 Created): {"id": 8, "project_id": 1, "title": "Проверить API", "status": "new", ...} Ошибки: 400 (не JSON), 422 (данные не прошли проверку).

10. Как искать ошибки

Общие правила из лабораторной работы №6 (точка с запятой, парные скобки, регистр букв, <?php в первой строке) действуют и здесь. Дополнительно для API:

  1. Если в ответ вместо JSON пришла страница с текстом ошибки PHP, откройте её: там указаны файл и строка.
  2. Ответ 400 почти всегда означает ошибку в вашем JSON: одинарные кавычки вместо двойных, запятая после последнего поля, лишний или пропущенный символ. В Postman выбран тип raw → JSON?
  3. Ответ 404 на правильный адрес: маршрут не зарегистрирован в routes/web.php или в адресе опечатка (/api/task вместо /api/tasks).
  4. Ответ 405: маршрут для этого метода не зарегистрирован (забыли строку $router->delete(...)). Заголовок Allow показывает, какие методы есть.
  5. Пустой ответ с кодом 200: метод контроллера ещё не написан (остался только комментарий с TODO).
  6. Смотрите в терминал, где запущен сервер: там для каждого запроса есть строка с адресом и кодом.
