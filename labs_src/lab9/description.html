Цель лабораторной работы

Объединить клиентскую и серверную части веб-приложения в единую систему: подключить клиент к настоящему REST API, реализовать авторизацию с разграничением прав по ролям, пройти полный пользовательский сценарий работы и выполнить комплексное тестирование.

В лабораторной работе №5 вы написали клиент, который общался с «сервером в браузере» (mock-api.js). В лабораторной работе №7 вы написали настоящий сервер, но проверяли его через Postman, а данные хранились в файлах. Теперь эти две части нужно подружить. Как правило, это сложнее, чем кажется: каждая часть работает сама по себе, а вместе они «не понимают» друг друга из-за мелких расхождений. Найти и устранить такие расхождения — главная практическая задача работы.

Постановка задачи

На основе клиентской части (лабораторная работа №5) и серверной части с REST API (лабораторная работа №7) необходимо выполнить интеграцию компонентов веб-приложения.

В ходе работы требуется:

  • подключить сервер к базе данных PostgreSQL (хранение данных, токенов и паролей в таблицах);
  • выполнить интеграцию клиента (frontend) и сервера (backend);
  • реализовать авторизацию пользователей: вход, защита API, роли;
  • реализовать и проверить полный пользовательский сценарий работы с системой;
  • выполнить комплексное тестирование: автоматические тесты API и сквозные сценарии в браузере.

Что будет и чего не будет в этой работе. Вы работаете на готовой заготовке: в ней есть клиент (экраны «Вход» и «Список задач»), сервер с API задач, проектов и участников, «охранник» для защиты адресов, SQL-скрипты базы данных, автотесты и скрипт сброса базы. Часть кода помечена TODO: это 11 небольших заданий в пяти частях. У каждого задания есть «Подсказка» с готовым кодом и строка «✔ Проверка», а остальной код уже написан: его нужно прочитать и понять. Сначала вы подключаете сервер к PostgreSQL (схема базы — из лабораторной работы №8), потом доделываете авторизацию и интеграцию на примере «Задачи команды», затем переносите те же приёмы на систему из ваших лабораторных работ №5, №7 и №8.

Теоретическая база

1. Как сервер работает с PostgreSQL

В лабораторной работе №7 сервер хранил данные в JSON-файлах, в лабораторной работе №8 вы спроектировали базу PostgreSQL. Теперь эти части соединяются: сервер хранит и берёт данные из базы. Устройство то же, что в лекции 2.2 (раздел «Как приложение работает с базой данных»): запрос проходит по слоям, и SQL написан только в одном из них.

СлойЧто делаетФайл в заготовке
контроллерпринимает запрос, проверяет данные, отвечает JSON; про SQL ничего не знаетapp/Controllers/Api/*ApiController.php
модель (репозиторий)единственное место, где написан SQL: «найти», «добавить», «изменить», «удалить»app/Models/PgRepository.php и модели TaskRepository, ProjectRepository, UserRepository

Благодаря слоям контроллеры и клиент почти не изменились: PgRepository даёт те же пять операций (all, find, add, update, delete), что и JsonRepository из лабораторной работы №7. Заменили «хранилище», остальное осталось прежним. В этом и польза слоёв.

$stmt = $pdo->prepare('SELECT id, title FROM tasks WHERE project_id = :project_id ORDER BY id'); // 1. запрос с «дыркой» :project_id $stmt->execute(['project_id' => $projectId]); // 2. значение передаётся отдельно $tasks = $stmt->fetchAll(); // 3. строки как массивы

Три правила работы с базой из PHP:

  • значения — только параметрами (:имя и execute([...])). Если склеить текст запроса со значением от пользователя ("... WHERE title = '$q'"), пользователь сможет вписать в поле свой SQL. Это SQL-инъекция, одна из самых опасных уязвимостей. С параметром значение никогда не становится частью команды;
  • имя таблицы или столбца параметром передать нельзя (например, в ORDER BY). Их берут из кода или проверяют по списку допустимых, как сделано для сортировки в TaskRepository::search();
  • RETURNING в конце INSERT и UPDATE возвращает строку целиком, с номером, который назначила база: отдельный SELECT не нужен.

Подключение. Параметры (адрес, порт, имя базы, пользователь, пароль) лежат в config/app.php и могут быть переопределены переменными окружения (DB_PORT=5433 php -S ...). База запускается командой docker compose up -d. Используется отдельная база taskapp, поэтому данные лабораторной работы №8 не затрагиваются.

Типы данных. PDO возвращает числа числами, а дату — строкой ГГГГ-ММ-ДД. Это совпадает с JSON из лабораторной работы №7, поэтому клиент не заметит подмены хранилища.

Ошибки базы. Если PostgreSQL не запущен, сервер отвечает клиенту 503 («База данных недоступна»): сервер жив, а хранилище нет. Это отличается от 500 (ошибка в коде сервера) и от «нет связи» (сервер недоступен вовсе).

2. Что значит «интегрировать» и что такое контракт

Клиент и сервер пишутся отдельно (часто — разными людьми), а работают вместе. Чтобы они понимали друг друга, нужна договорённость — контракт: какие бывают адреса, какие в них данные, как называются поля, в каком виде приходят ошибки. Это как розетка и вилка: каждая сама по себе исправна, но если не совпадает форма штырьков, ток не пойдёт.

Ошибки интеграции обычно не «громкие»: ничего не падает, просто что-то не показывается или не сохраняется. Поэтому главный инструмент интеграции — вкладка Network в браузере: она показывает, что клиент на самом деле отправил и что сервер ответил.

Когда что-то не работает, задайте два вопроса: что клиент отправил? и что ответил сервер? Ответ на них есть во вкладке Network (раздел 11 «Как искать ошибки»). Договорённости записаны в docs/api.md: это единый источник правды для обеих частей. Правило: API — главный, клиент подстраивается под него, а не наоборот.

3. Как клиент получает ответ и что показать пользователю

Запрос с клиента выполняет функция fetch (лабораторная работа №5). У неё есть особенность: она считает ошибкой только отсутствие связи, а ответы с кодами 401, 404, 422, 500 для неё «успешные» (сервер ведь ответил). Аналогия. Проходная в офисе. Охранник сначала проверяет пропуск (аутентификация): нет пропуска — вас не пустят вообще (401). Дальше у каждого пропуска свои двери (авторизация): бухгалтеру в серверную нельзя (403).

5. Как работает вход по токену

Отправлять пароль с каждым запросом неудобно и опасно. Вместо этого пароль проверяется один раз при входе, а дальше клиент предъявляет токен — длинную случайную строку, «временный пропуск». Порядок такой:

  1. клиент отправляет POST /api/auth/login с email и паролем;
  2. сервер находит участника, сверяет пароль и создаёт токен (случайные 64 символа) со сроком действия;
  3. сервер возвращает токен и данные участника; клиент запоминает их в localStorage;
  4. с каждым следующим запросом клиент добавляет заголовок Authorization: Bearer <токен>;
  5. «охранник» на сервере проверяет токен: если он не найден или просрочен — ответ 401, если подходит — запрос идёт дальше к контроллеру;
  6. при выходе сервер забывает токен: после этого он недействителен, даже если его кто-то скопировал.

Токен и сессия PHP. В лекции 3.1 вы видели сессии: PHP выдаёт браузеру номер сессии в cookie и хранит данные на сервере. Идея та же («пропуск»), но токен удобнее для API: его добавляет в заголовок сам JavaScript-код клиента, и сервер не зависит от cookie. Для мобильных приложений и клиентов на других адресах это важно.

POST /api/auth/login { "email": "anna@example.com", "password": "123456" } 200 OK { "token": "d6c99ce91e…", "expires_at": "2026-10-27T20:51:55+00:00", "user": { "id": 1, "name": "Анна Петрова", "email": "anna@example.com", "role": "manager" } } GET /api/tasks Authorization: Bearer d6c99ce91e… ← так выглядит каждый следующий запрос

6. Пароли: как их хранить

Пароль нельзя хранить открытым текстом: если базу украдут, злоумышленник получит пароли всех пользователей (а люди часто используют один пароль на многих сайтах). Хранят хеш — результат необратимого преобразования. Из хеша пароль восстановить нельзя, но можно проверить: хешируем введённый пароль и сравниваем. В PHP для этого две функции:

$hash = password_hash('123456', PASSWORD_DEFAULT); // при создании пользователя: сохраняем $hash // $2y$10$haEK45zG.lxMr2bCMvnFHe733nBjr19uAjNxxC/GGGv0QMbvc5wpq password_verify('123456', $hash); // при входе: true, если пароль подходит password_verify('другой', $hash); // false

Правила: хеш хранится в таблице users (столбец password_hash), но никогда не отправляется клиенту; при неверном входе сообщение одно и то же («Неверный email или пароль») независимо от того, ошиблись в почте или в пароле: так нельзя узнать, какие адреса зарегистрированы.

7. Токен: срок жизни, хранение, отзыв

  • Случайность. Токен создаётся функцией random_bytes (криптографически стойкий генератор). Угадать его нельзя; придумывать «свой» токен из номера и времени нельзя.
  • Срок. Токен действует ограниченное время (в заготовке 2 часа, token_ttl в config/app.php). Украденный токен перестанет работать сам.
  • Хеш на сервере. В таблице auth_tokens лежит не сам токен, а его хеш (sha256). Если база утечёт, войти по ней нельзя.
  • Отзыв. При выходе (POST /api/auth/logout) токен удаляется. Если клиент только сотрёт токен у себя, на сервере он останется рабочим до конца срока.
  • Хранение в браузере. Клиент держит токен в localStorage. Это просто, но если на страницу удастся внедрить чужой JavaScript (атака XSS), он сможет прочитать токен. Поэтому всё, что приходит от пользователя, выводится на страницу через escapeHtml() (так сделано в app.js). В крупных системах токен кладут в cookie с флагом HttpOnly, который недоступен JavaScript (разберёте в задании повышенной сложности).
  • HTTPS. По незащищённому HTTP токен и пароль можно подсмотреть в сети. В учебной работе мы работаем по HTTP на своём компьютере, в реальной системе — только HTTPS.

8. Роли и права

У каждого участника есть роль, а у роли — набор разрешённых действий. В заготовке три роли:

На сервере право проверяется одной строкой в начале метода: require_role('manager'); (если роль не подходит, функция сама отвечает 403 и дальше код не выполняется). На клиенте по роли скрывают лишние кнопки («Удалить» видит только руководитель).

Скрытая кнопка — не защита. Любой пользователь может отправить запрос в обход вашего интерфейса (curl, консоль браузера). Скрытие кнопок — удобство, чтобы человек не нажимал на то, что всё равно не сработает. Настоящая защита — только проверка на сервере. Поэтому в тестах есть прямые запросы с токеном разработчика.

9. Откуда загружена страница: CORS

Браузер защищает пользователя правилом: страница, загруженная с одного адреса (http://localhost:5500), не может читать ответы с другого адреса (http://localhost:8000), пока сервер не разрешит. Адрес — это протокол, имя и порт вместе. Если клиент и API на одном адресе (так в заготовке: http://localhost:8000/client/ и http://localhost:8000/api/...), проблем нет.

Если адреса разные, сервер должен прислать заголовки Access-Control-Allow-Origin и другие. Это называется CORS. Перед «непростым» запросом (например, с заголовком Authorization) браузер сам отправляет пробный запрос OPTIONS (preflight): «можно ли мне так?» Сервер отвечает 204 с разрешающими заголовками. В заготовке всё это уже написано: достаточно перечислить разрешённые адреса клиентов в config/app.php → cors_origins.

Как выглядит ошибка CORS. Клиент пишет «Нет связи с сервером», хотя сервер работает. В консоли браузера: Access to fetch at 'http://localhost:8000/api/auth/login' from origin 'http://localhost:5500' has been blocked by CORS policy: ... No 'Access-Control-Allow-Origin' header is present. Исправляется на сервере, а не в клиенте.

10. Комплексное тестирование

Комплексное тестирование проверяет не отдельные функции, а систему целиком: работает ли цепочка «пользователь — клиент — сервер — данные» в нужных сценариях. Проверок бывает много, поэтому часть из них поручают программе. В этой работе три уровня:

УровеньЧто проверяетЧемКогда запускать
автоматические тесты APIсервер: коды ответов, права, формат данныхскрипт tests/api-tests.phpпосле каждого изменения сервера (секунды)
сквозные сценарииклиент вместе с сервером, глазами пользователявы руками в браузере по таблице сценариевперед сдачей, после крупных изменений клиента
проверки безопасностипароли, токены, права, защита от XSSпросмотр файлов, прямые запросы, консольперед сдачей

Какие бывают проверки. Позитивные проверяют, что нормальное действие работает (вход с верным паролем — 200). Негативные проверяют, что неправильное действие отклонено (неверный пароль — 401, чужая роль — 403, пустое название — 422). Новички пишут только позитивные, а ошибки живут в негативных. Хороший набор содержит обе группы.

Как устроен автоматический тест. Тест — это запрос и проверка ответа. В заготовке для этого есть три функции:

$r = call('POST', '/api/auth/login', ['email' => 'anna@example.com', 'password' => 'неверный']); // отправить запрос expectStatus('вход с неверным паролем', 401, $r); // проверить код ответа check('сообщение не раскрывает, что неверно', $r['json']['error'] === 'Неверный email или пароль'); // проверить любое условие

Результат — строки PASS (проверка прошла) и FAIL (не прошла) с пояснением, а в конце итог. Если FAIL, сначала решите, что неверно: код сервера или сам тест. Тесты можно запускать сколько угодно раз: в начале данные сбрасываются к исходным.

Как записывать сквозной сценарий. Каждая строка таблицы — это один тест-кейс: номер, что проверяем, шаги, ожидаемый результат, фактический результат. Ожидаемый результат записывайте до выполнения шагов: так вы проверяете систему, а не подгоняете описание под то, что увидели.

№СценарийШагиОжидаемый результатРезультат
A2Неверный парольввести пароль 000000, «Войти»под формой «Неверный email или пароль»; в Network ответ 401пройден / не пройден

11. Как искать ошибки: вкладка Network

Откройте страницу клиента, нажмите F12, перейдите на вкладку Network и обновите страницу (если запросов нет, обновите страницу при открытой вкладке). Каждая строка — один запрос. Щёлкните по ней:

Вкладка запросаЧто смотреть
Headersадрес, метод, код ответа (Status Code); в разделе Request Headers — есть ли Authorization: Bearer ...
Payloadчто клиент отправил в теле запроса: имена полей, типы (строка или число), пустые значения
Response / Previewчто ответил сервер: JSON с данными или с ошибкой error, errors

Полезные приёмы:

  • Console. Красные строки — исключения JavaScript и ошибки CORS. Любой ответ можно проверить прямо в консоли, например: getTasks('', '').then(console.log);
  • Application → Local Storage (или в консоли localStorage): есть ли token и user. Чтобы «испортить» токен: localStorage.setItem('token', 'bad');
  • Network → переключатель Offline (или список «No throttling» → Offline): имитация пропавшей связи;
  • Disable cache (галочка на вкладке Network) и обновление страницы по Ctrl+Shift+R (на macOS Cmd+Shift+R): иначе браузер может показывать старую версию файлов app.js и api.js;
  • тот же запрос через curl: если в curl работает, а в клиенте нет, ошибка в клиенте (заголовки, поля, тело); если не работает и там, и там — на сервере.
Что видитеВероятная причина
ответ 503 «База данных недоступна»PostgreSQL не запущен или неверные параметры подключения: docker compose ps, docker compose up -d, проверьте config/app.php
клиент пишет «Нет связи с сервером», сервер запущенклиент на другом адресе и не настроен CORS (см. консоль); или адрес API_BASE неверен
после входа список пуст или «Требуется авторизация»токен не отправляется: нет заголовка Authorization; или токен не сохранился (посмотрите localStorage)
создание задачи всегда отвечает 422в Payload не те имена полей, номер проекта строкой вместо числа, пустая дата "" вместо null
запрос уходит, в консоли Unexpected token < in JSONвместо JSON пришла страница с ошибкой PHP (откройте Response: там файл и строка)
изменили app.js, а ничего не поменялосьбраузер показывает старую копию: Ctrl+Shift+R
в Network запрос OPTIONS перед основнымэто preflight (раздел 9), его отправляет браузер, а не ваш код
сервер «завис» и не отвечает на запросы браузеравстроенный сервер PHP обрабатывает по одному запросу, а Chrome открывает «запасные» соединения заранее. Запустите: PHP_CLI_SERVER_WORKERS=4 php -S localhost:8000 -t public. В Windows этот режим не поддерживается: остановите сервер (Ctrl+C) и запустите снова; помогает и открытие клиента по адресу http://127.0.0.1:8000/client/

Повышенная сложность (по желанию)

  • клиент на другом адресе: запустите клиент отдельно (php -S localhost:5500 -t public/client), укажите API_BASE в config.js и разрешите адрес клиента в cors_origins; убедитесь, что без разрешения вы видите ошибку CORS из раздела 9;
  • ограничение попыток входа: после 5 неверных паролей подряд вход для этой почты блокируется на 1 минуту (ответ 429);
  • смена пароля: POST /api/auth/password со старым и новым паролем и форма в клиенте; после смены остальные токены участника отзываются;
  • «Запомнить меня»: срок токена 30 дней вместо 2 часов, если отмечена галочка;
  • cookie вместо localStorage: выдавать токен в cookie с флагами HttpOnly и SameSite и написать в отчёте, какие угрозы это снимает, а какие появляются (CSRF);
  • экран управления участниками для руководителя (список, добавление, смена роли);
  • индекс для поиска: выполните EXPLAIN ANALYZE запроса поиска title ILIKE '%текст%' на большом числе задач (скрипт генерации — в лабораторной работе №8) и ускорьте его расширением pg_trgm и индексом GIN; опишите результат;
  • исполнитель задачи: добавьте в tasks столбец assignee_id (внешний ключ на users, ON DELETE SET NULL), поле в форму клиента и запрос «мои задачи» (GET /api/tasks?assignee=me);
  • ошибки базы в ответах API: нарушение уникальности (SQLSTATE 23505) и внешнего ключа (23503) превращайте в ответ 409 вместо 500;
  • журнал входов: записывайте в файл время, почту и результат каждой попытки входа (без паролей).
