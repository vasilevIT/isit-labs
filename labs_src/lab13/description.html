Цель лабораторной работы

Изучить принципы работы полнотекстового поиска, подключить OpenSearch, выполнить индексацию данных информационной системы и реализовать поиск по содержимому приложения.

Сейчас поиск в вашем приложении устроен просто: WHERE title ILIKE '%текст%'. Он находит только точную подстроку в названии: слово «форма» не найдёт задачу «Подключить форму», опечатка «форсма» не найдёт ничего, а о том, какой результат важнее, он не знает. В этой работе вы подключите специальный поисковый сервер OpenSearch, научите приложение складывать в него копии задач и искать по ним так, как привыкли пользователи поисковиков: с учётом форм слов, опечаток, важности полей и с подсветкой найденного.

Теоретическая база

Основная теория — в лекции 4.1 «Поиск, аналитика и работа с большими объёмами данных». Здесь самое необходимое для работы.

1. Чем полнотекстовый поиск отличается от ILIKE

Оператор ILIKE '%текст%' ищет подстроку: слово как набор символов. Человек ищет иначе: по смыслу слов, независимо от падежа и порядка, с опечатками, и хочет увидеть самое подходящее первым.

Что нужно пользователюILIKE по названиюПолнотекстовый поиск
«форма» должна найти «Подключить форму»нет: «форма» и «форму» — разные строкида: слова приводятся к основе
«авторизации экран» должно найти «экран авторизации»нет: подстрока должна совпасть целикомда: порядок слов не важен
опечатка «форсма»нетда: нечёткий поиск (fuzziness)
слово из описания или названия проектанет (ищем только в названии)да: поиск сразу по нескольким полям
самое подходящее — первымнет: порядок по номеруда: результаты упорядочены по релевантности
показать, что именно нашлосьнетда: подсветка слов в тексте
скорость на миллионах записейпросматривает всю таблицуищет по готовому индексу

Недостатки: нужен ещё один сервер, копия данных может ненадолго отставать от базы (см. раздел 5), поиск нужно настраивать. Поэтому полнотекстовый поиск оправдан, когда пользователи ищут по тексту, а не по номеру или точному значению.

2. Как устроен полнотекстовый поиск

Аналогия. Предметный указатель в конце учебника: слово, а рядом номера страниц, где оно встречается. Чтобы найти слово, не нужно перечитывать книгу: открываешь указатель. Поисковый индекс — такой же указатель, только автоматический. Его называют инвертированным: не «документ → слова», а «слово → документы».

Перед тем как попасть в указатель, текст проходит анализатор:

  1. разбивается на слова (токены): «Подключить форму обратной связи» → подключить, форму, обратной, связи;
  2. приводится к нижнему регистру;
  3. слова сводятся к основе (стемминг): «форма», «формы», «формой» → «форм»;
  4. служебные слова («и», «в», «на», «для»), которые не несут смысла, отбрасываются.

Тот же анализатор применяется к запросу. Поэтому запрос «форма» и текст «форму» превращаются в одну основу «форм» и совпадают.

Основа (слово в указателе)В каких задачах встречается
форм№2 «Подключить форму обратной связи»
экран№4 «Спроектировать экран авторизации»
авторизац№4 «Спроектировать экран авторизации»
портал№7 (в названии проекта «Внутренний портал»)

Релевантность. Из найденных задач важно показать первой самую подходящую. OpenSearch оценивает каждую найденную запись числом (score, алгоритм BM25). Грубо: чем реже слово встречается во всех документах, тем оно ценнее (редкое слово «авторизации» говорит больше, чем частое «задача»); чем чаще слово встречается в этом документе и чем он короче, тем оценка выше. Кроме того, поля можно сделать важнее одно другого (вес поля): совпадение в названии ценнее, чем в описании.

3. OpenSearch: индекс, документ, структура индекса

OpenSearch — свободный поисковый сервер (ответвление Elasticsearch). Это отдельная программа, как PostgreSQL: приложение подключается к ней по сети (порт 9200) и разговаривает по HTTP: отправляет JSON, получает JSON. Попробовать можно обычным curl.

ТерминЧто это простыми словамиАналог в PostgreSQL
индекснабор однотипных документов с общей структуройтаблица
документодна запись в виде JSON; у него есть номер (_id)строка
mappingописание полей индекса: какого типа и как обрабатыватьCREATE TABLE
псевдоним (alias)второе имя индекса; позволяет подменять индекс, не меняя код—

Типы полей. Главное различие: text — текст, который разбирается на слова и ищется по словам (название, описание); keyword — значение целиком, без разбора (статус, приоритет): по нему не ищут, а фильтруют и группируют. Есть также integer, date и другие.

# версия и живость сервера curl http://localhost:9200 # положить документ № 1 в индекс demo (индекс создастся сам, но с угаданной структурой: так делать не стоит) curl -X PUT "http://localhost:9200/demo/_doc/1?refresh=true" -H "Content-Type: application/json" -d '{"title": "Подключить форму обратной связи"}' # найти curl -X POST "http://localhost:9200/demo/_search?pretty" -H "Content-Type: application/json" -d '{"query": {"match": {"title": "форма"}}}' # посмотреть, как анализатор разбирает текст curl -X POST "http://localhost:9200/_analyze?pretty" -H "Content-Type: application/json" -d '{"analyzer": "russian", "text": "формы формой"}'

Анализатор russian входит в OpenSearch. Попробуйте _analyze с разными текстами и убедитесь, что «форма», «формы» и «формой» превращаются в одно слово.

Псевдоним. Приложение всегда обращается к псевдониму tasks, а настоящие индексы называются tasks_v<время>. Когда структуру индекса нужно изменить или данные перестроить заново, создаётся новый индекс, а псевдоним переключается на него одной неделимой операцией: поиск ни на секунду не остаётся без данных. Старый индекс после этого удаляется.

4. Запрос поиска

Запрос к OpenSearch — это JSON, в котором описано, что искать. Нам нужны четыре возможности:

ВозможностьКак записывается
искать слова сразу в нескольких полях с разной важностьюmulti_match с fields: ["title^3", "project_title^2", "description"] (число после ^ — вес поля)
прощать опечаткиfuzziness: "AUTO": допускается 1–2 ошибки в слове в зависимости от его длины
фильтровать, не влияя на оценкуbool.filter с условиями term по status и project_id
выводить по страницам и подсвечивать найденноеfrom и size; блок highlight (найденные слова в тегах <mark>)
{ "from": 0, "size": 10, "track_total_hits": true, "query": { "bool": { "must": [ { "multi_match": { "query": "форма", "fields": ["title^3", "project_title^2", "description"], "fuzziness": "AUTO" } } ], "filter": [ { "term": { "status": "in_progress" } } ] } }, "highlight": { "encoder": "html", "pre_tags": ["<mark>"], "post_tags": ["</mark>"], "fields": { "title": {}, "description": {} } } }

В ответе: hits.total.value — сколько найдено, hits.hits[] — найденные документы, у каждого _score (оценка), _source (сам документ) и highlight (фрагменты с подсветкой).

Безопасность подсветки. Подсветка вставляет в текст теги <mark>, а результат выводится на страницу как HTML. Если в названии задачи написано <script>...</script>, без защиты оно попало бы на страницу как код (XSS). Параметр "encoder": "html" заставляет OpenSearch заменять опасные символы в тексте на безопасные коды, а настоящими остаются только теги <mark>. Автотесты проверяют это.

5. Индексация: как копия попадает в OpenSearch и не расходится с базой

Источник правды — PostgreSQL. Всё, что есть в OpenSearch, можно в любой момент восстановить из базы. Поэтому поисковая копия — «одноразовая»: если с ней что-то не так, перестраиваем.

СпособКак работаетГде в работе
полная переиндексациячитаем все задачи из PostgreSQL пачками, загружаем в новый индекс операцией _bulk (много документов одним запросом), переключаем псевдонимphp bin/reindex.php, Search::reindexAll
синхронизация при изменениипри создании, изменении, удалении задачи и переименовании проекта в очередь ставится задача search_index; воркер обновляет документSearchIndexJob

Почему через очередь, а не прямо в запросе? Обращение к OpenSearch — ещё один сетевой вызов, который может быть медленным или завершиться ошибкой. Если пользователь ждёт его в запросе, то сбой поискового сервера превратится в сбой сохранения задачи. Через очередь (лабораторная работа №11) пользователь получает ответ сразу, а воркер при ошибке повторит попытку.

Что кладём в задачу очереди. Не «что изменилось», а «какую задачу проверить» (task_id). Воркер сам смотрит в PostgreSQL, какова задача сейчас: есть — кладёт свежую версию в индекс, нет — удаляет документ. Благодаря этому порядок выполнения задач не важен, повтор безопасен (идемпотентность), а индекс всегда получает самые свежие данные. Если проект переименовали, обновляются документы всех его задач: название проекта хранится внутри каждого документа.

Согласованность в конечном счёте. Между изменением в базе и появлением изменения в поиске проходит время: пока задача лежит в очереди и пока OpenSearch обновляет свой индекс (по умолчанию раз в секунду). Для поиска это нормально: пользователь, который только что создал задачу, ищет её через несколько секунд, а не мгновенно. Если нужно, чтобы документ был виден сразу, используют параметр refresh=wait_for, но на каждый документ так делать дорого; в нашей работе так сделано для одиночных операций воркера.

Что делать, если копия разошлась с базой (воркер был выключен, очередь потеряла задачу, Redis недоступен при постановке): выполнить php bin/reindex.php. Это нормальная «лечебная» процедура, а не признак поломки.

6. Поиск не должен ронять приложение

Поиск — удобство, а не основа системы. Если OpenSearch выключен или недоступен, пользователь всё равно должен иметь возможность что-то найти. В работе это сделано так:

  • подключение с коротким таймаутом (1 секунда): недоступный сервер не «вешает» запрос;
  • метод Search::request при отсутствии связи бросает исключение с кодом 503;
  • обработчик поиска ловит 503 и выполняет запасной поиск в PostgreSQL (ILIKE по названию): ответ имеет тот же вид, а заголовок X-Search-Engine: postgres и поле engine честно сообщают, что поиск упрощённый;
  • ошибки другого рода (неверный запрос, ошибка в коде) не прячутся: иначе они остались бы незамеченными.

Права доступа. OpenSearch сам не знает, кому какие задачи можно видеть: в индекс попало всё. В нашей системе все участники видят все задачи, поэтому фильтровать нечего. Если бы у задач были права, фильтр по доступу пришлось бы добавлять в каждый поисковый запрос (или хранить права в документе).

Журнал поиска. Каждый поисковый запрос записывается в журнал событий (лабораторная работа №12): что искали, сколько нашли, сколько заняло. Это ценные данные: частые запросы показывают, что нужно людям, а запросы без результата (found = 0) показывают, чего не хватает в системе или поиске. Запросы могут содержать личные данные, поэтому длинные запросы обрезаются, а журнал читает только руководитель.

7. Как проверять качество и скорость поиска

Поиск нельзя проверить одним запросом. Нужен набор контрольных запросов с известным ожидаемым результатом:

ПроверкаПримерЧто ожидается
словоформа«форма» при задаче «Подключить форму»задача найдена
опечатка«форсма»та же задача найдена

Скорость. На семи задачах разницы в скорости нет: нужны данные. Скрипт bin/load-searchdata.php создаёт задачи со «живыми» названиями и описаниями (в отличие от одинаковых «Тестовая задача №N» из лабораторной работы №10), а bin/search-compare.php показывает для каждого запроса, сколько находит и за сколько миллисекунд отвечает каждый способ. Честный вывод по результатам может оказаться неожиданным: на ста тысячах задач ILIKE по одному полю ещё достаточно быстр, и главный выигрыш OpenSearch не в скорости, а в качестве поиска (формы слов, опечатки, релевантность, поиск по нескольким полям). Описывайте то, что измерили, а не то, что ожидали.

Шаг 0. Подготовка и запуск

  1. Скопируйте заготовку в каталог lab13/src/ своего репозитория, сделайте первый коммит и откройте папку в VS Code.
  2. Запустите PostgreSQL, Redis и OpenSearch: в папке lab13/src выполните docker compose up -d. Если порты 5432, 6379 или 9200 заняты (контейнер из лабораторной работы №12, свой Redis), остановите их или используйте другие порты: DB_PORT=5433 REDIS_PORT=6380 OPENSEARCH_PORT=9201 docker compose up -d; те же значения передавайте серверу, воркеру и скриптам. OpenSearch стартует 20–60 секунд: проверьте curl http://localhost:9200, пока не придёт JSON с версией. Если контейнер завершился (docker compose ps), смотрите docker compose logs opensearch: чаще всего не хватило памяти (код 137).
  3. Создайте таблицы и загрузите данные: php bin/reset-db.php. Строка «индекс поиска не обновлён: ...» сейчас нормальна: поисковый код ещё не написан. Запустите сервер из папки lab13/src: PHP_CLI_SERVER_WORKERS=4 php -S localhost:8000 -t public, а в другом окне воркер: php bin/worker.php (если на порту 8000 остался сервер от прошлой работы, остановите его: pkill -f "php -S localhost:8000", иначе вы проверяете старый код).
  4. Откройте http://localhost:8000/client/, войдите (anna@example.com, пароль 123456): система работает как раньше; в блоке «Поиск по задачам» поиск пока ничего не найдёт (на сервере код 501). В другом окне выполните php tests/api-tests.php: сейчас проходят 178 проверок из 224. Это ваш «прогресс-бар». (Воркер на время тестов остановите: тесты запускают его сами.)
  5. Изучите app/Core/Search.php (заготовки методов) и config/app.php (блок search). Поиграйте с OpenSearch руками командами из теории (раздел 3): положите документ, найдите его, посмотрите _analyze. Потом удалите игрушечный индекс: curl -X DELETE http://localhost:9200/demo.

Требования к оформлению

Результаты лабораторной работы должны быть оформлены в виде Git-репозитория. Рекомендуется делать отдельные коммиты после каждого шага.

Рекомендуемая структура:

lab13/ ├── README.md ├── src/ # приложение (в том числе docker-compose.yml, sql/, bin/, tests/) ├── images/ # скриншоты и диаграммы └── docs/ └── search.md # структура индекса, индексация, поиск, сравнение с ILIKE, выводы

Файл README.md должен содержать:

  • название лабораторной работы;
  • цель работы;
  • описание структуры поискового индекса (поля, типы, анализатор, обоснование);
  • описание процесса индексации данных (полная переиндексация, синхронизация при изменениях, согласованность);
  • описание реализации полнотекстового поиска (запрос, веса, фильтры, подсветка, запасной режим);
  • результаты проверки (контрольные запросы, сравнение с ILIKE, автотесты);
  • вывод.

При оформлении рекомендуется использовать язык разметки Markdown, заголовки, списки и таблицы, сопровождать описание скриншотами и пояснениями, придерживаться понятной структуры каталогов и файлов.
