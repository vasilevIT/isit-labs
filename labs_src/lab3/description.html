Лабораторная работа №3

Проектирование архитектуры информационной системы

Модуль: Архитектура современных информационных систем

Тема: Архитектура веб-систем: клиент, сервер и API

Продолжительность: 4 академических часа

Цель лабораторной работы

Изучить принципы проектирования архитектуры информационных систем, определить структуру приложения, спроектировать взаимодействие между основными компонентами и подготовить структуру программного проекта для дальнейшей разработки.

Необходимое программное обеспечение

  • Git, GitHub-аккаунт;
  • IDE, PHP;
  • Visual Studio Code (или другой редактор кода);
  • редактор диаграмм (diagrams.net (draw.io), PlantUML, Mermaid или аналог);
  • веб-браузер.

Постановка задачи

На основе результатов предыдущих лабораторных работ необходимо разработать архитектуру информационной системы. В ходе работы требуется:

  • определить архитектурный стиль приложения;
  • выделить основные компоненты системы;
  • описать взаимодействие между компонентами;
  • определить и отразить в архитектуре одну нетиповую особенность своей предметной области (подробнее — в разделе теории «Индивидуальная особенность вашей предметной области»);
  • разработать структуру проекта;
  • подготовить репозиторий для дальнейшей реализации информационной системы.

В качестве архитектуры рекомендуется использовать трёхуровневую архитектуру веб-приложения: клиентская часть (Frontend), серверная часть (Backend), база данных (Database).

Теоретическая база

1. Что такое архитектурный стиль

Архитектура информационной системы — это принципиальная схема организации системы, определяющая, из каких частей (компонентов) она состоит и как эти части взаимодействуют между собой. Выбор архитектурного стиля влияет на то, насколько легко систему разрабатывать, тестировать, масштабировать и поддерживать.

Самый распространённый стиль для веб-приложений — трёхуровневая (3-tier) архитектура, в которой приложение делится на три независимых уровня:

  • Frontend (клиентская часть) — то, что видит и с чем взаимодействует пользователь (веб-интерфейс, мобильное приложение);
  • Backend (серверная часть) — обработка запросов, бизнес-логика, проверка прав доступа;
  • Database (база данных) — постоянное хранение данных.

Преимущество такого разделения: каждый уровень можно разрабатывать, тестировать и масштабировать независимо от остальных.

Пример архитектурной схемы (абстрактный):

На этой схеме:

  • пользователь взаимодействует только с Frontend;
  • Frontend обращается к Backend по протоколу HTTP (REST API);
  • Backend обрабатывает бизнес-логику и обращается к Database для чтения/записи данных.

2. Компоненты системы и их ответственность

Компонент — это логически обособленная часть системы, отвечающая за конкретную функцию: например, за обработку HTTP-запросов, за бизнес-правила или за доступ к данным. Хорошая практика — чтобы каждый компонент отвечал только за одну зону ответственности (принцип единственной ответственности).

Типичные компоненты серверной части (backend):

  • Контроллеры — принимают HTTP-запросы, вызывают нужную бизнес-логику, формируют ответ;
  • Сервисы — содержат бизнес-логику приложения (правила, вычисления, проверки);
  • Репозитории — отвечают за доступ к данным (запросы к базе данных);
  • Модели — описывают структуру данных предметной области.

3. Взаимодействие компонентов и диаграмма взаимодействия (Sequence Diagram)

Чтобы понять, как компоненты системы работают вместе при обработке конкретного запроса пользователя, используется диаграмма взаимодействия (Sequence Diagram). Она показывает участников (пользователя, компоненты системы) и последовательность сообщений (вызовов), которыми они обмениваются во времени — сверху вниз.

Диаграмма взаимодействия отвечает на вопросы: какой компонент вызывается первым, что он передаёт следующему компоненту, в каком порядке происходит обращение к базе данных, что возвращается пользователю.

Пример диаграммы взаимодействия (абстрактный):

На этой диаграмме:

  • Участники (прямоугольники сверху) — Пользователь, Клиент, Сервер, База данных;
  • Вертикальные линии («линии жизни») показывают время существования участника в рамках сценария;
  • Стрелки показывают сообщения (вызовы) — сплошные стрелки для запросов, пунктирные — для ответов;
  • Порядок стрелок сверху вниз соответствует реальной последовательности обработки запроса.

4. Структура проекта

Структура каталогов проекта должна отражать логическое разделение приложения на модули, соответствующее выбранной архитектуре. Например, для трёхуровневой архитектуры типична структура, где backend разбит на подкаталоги по типу компонентов (controllers, services, repositories, models, routes).

project/ ├── frontend/ ├── backend/ │ ├── controllers/ │ ├── services/ │ ├── repositories/ │ ├── models/ │ └── routes/ ├── database/ ├── docs/ └── README.md

5. Индивидуальная особенность вашей предметной области

Что считается «нетиповой особенностью»? Это какая-то функция вашей системы, для реализации которой одного простого запроса к базе данных недостаточно. Обычно это одно из следующего:

  • Обработка данных в фоне (асинхронная задача). Например, генерация отчёта, пересчёт статистики, массовая рассылка — операция, которая выполняется долго и не должна заставлять пользователя ждать ответа страницы;
  • Уведомления в реальном времени. Например, мгновенное оповещение пользователя о новом сообщении, изменении статуса заказа или задачи (через WebSocket, push-уведомления или похожий механизм);
  • Работа с файлами. Например, загрузка изображений, документов, вложений — требует отдельного хранилища файлов и модуля, который отвечает за приём, проверку и выдачу файлов;
  • Интеграция с внешним сервисом. Например, отправка Email/SMS, приём онлайн-оплаты, обращение к внешнему API (карты, курсы валют, погода и т.д.);
  • Промежуточное хранение данных (кэш). Например, кэширование часто запрашиваемых данных, чтобы не обращаться к базе данных при каждом запросе;
  • Сложный поиск или фильтрация. Например, полнотекстовый поиск по большому количеству записей, который требует отдельного индекса или поискового движка, а не обычного SQL-запроса.

Как это выбрать под свою предметную область? Посмотрите на функции своей системы (они уже должны быть определены в лабораторных работах №1–2) и найдите ту, которая явно выделяется среди остальных «просмотреть список / открыть карточку / сохранить форму». Несколько примеров:

Предметная областьПример нетиповой особенности
Интернет-магазинотправка Email/SMS о статусе заказа при изменении его состояния (интеграция с внешним сервисом)
Система бронированияпроверка занятости ресурса на конкретную дату/время «на лету», чтобы избежать двойного бронирования
Учебная платформагенерация и выдача сертификата (PDF-файла) после завершения курса
Служба поддержкимгновенное уведомление сотрудника о новой заявке (реальное время)
Система управления задачамиуведомление ответственного при назначении задачи или приближении срока

Что нужно сделать в отчёте. Для выбранной особенности:

  1. кратко опишите, в чём она заключается и почему она важна именно для вашей предметной области;
  2. укажите, какой компонент (существующий или новый) отвечает за её реализацию — например, «Модуль уведомлений», «Модуль работы с файлами», «Модуль интеграции с платёжным сервисом»;
  3. отразите этот компонент на диаграмме архитектуры (Шаг 5) и, если особенность связана со сценарием из диаграммы взаимодействия, покажите её и там.

Не нужно реализовывать эту функцию программно на этом этапе — лабораторная работа посвящена проектированию, а не разработке. Важно только осознанно выделить особенность и показать её место в архитектуре.

Этапы выполнения

Шаг 1. Выбор архитектуры приложения

Определите архитектурный стиль будущей информационной системы. Кратко опишите: тип приложения, основные уровни архитектуры, назначение каждого уровня, преимущества выбранного подхода.

Шаг 2. Определение компонентов системы

Выделите основные компоненты приложения. Например: пользовательский интерфейс, API, бизнес-логика, модуль работы с данными, база данных, файловое хранилище, внешние сервисы (при наличии). Для каждого компонента опишите его назначение и ответственность.

Шаг 3. Проектирование взаимодействия компонентов

Опишите, каким образом взаимодействуют основные компоненты системы. Определите: направление передачи данных, последовательность обработки пользовательского запроса, взаимодействие с базой данных, взаимодействие с внешними сервисами (при наличии). При необходимости постройте диаграмму взаимодействия компонентов.

Шаг 4. Определение индивидуальной особенности вашей предметной области

Найдите в своей предметной области одну функцию, которая не сводится к типовому CRUD (см. раздел теории «Индивидуальная особенность вашей предметной области»). Определите, какой компонент отвечает за её реализацию, и отразите его на диаграмме архитектуры.

Шаг 5. Подготовка структуры проекта

Разработайте структуру каталогов будущего проекта, отражающую логическое разделение приложения на основные модули. При необходимости структура может быть адаптирована под выбранную технологию.

Шаг 6. Подготовка архитектурных схем

Разработайте диаграмму архитектуры системы и диаграмму взаимодействия компонентов. Диаграммы могут быть выполнены в draw.io, Mermaid или PlantUML.

Шаг 7. Подготовка итогового отчёта

Оформите результаты работы в виде Git-репозитория с использованием Markdown.

Что должно получиться в результате

  • описание архитектуры приложения;
  • перечень компонентов системы;
  • описание взаимодействия компонентов;
  • описание индивидуальной особенности предметной области и отвечающего за неё компонента;
  • структура проекта;
  • диаграмма архитектуры;
  • диаграмма взаимодействия компонентов.

Домашняя доработка

  • доработать схему;
  • добавить описание API;
  • подготовить проект к следующей лабораторной работе.

Требования к оформлению

Результаты лабораторной работы должны быть оформлены в виде Git-репозитория.

Рекомендуемая структура:

lab3/ ├── README.md ├── diagrams/ ├── images/ └── src/ (при наличии)

Файл README.md должен содержать:

  • название лабораторной работы;
  • цель работы;
  • краткое описание выполненного задания;
  • основные результаты работы;
  • диаграммы, схемы или иллюстрации (при наличии);
  • вывод.

При оформлении рекомендуется:

  • использовать язык разметки Markdown;
  • применять заголовки, списки и таблицы;
  • сопровождать схемы кратким описанием;
  • придерживаться понятной структуры каталогов и файлов.
