1. Алгоритм кеширования (cache-aside)

Кеш — быстрое хранилище копий данных, которые часто нужны и долго достаются из базы. Redis хранит данные в оперативной памяти, поэтому отвечает за доли миллисекунды (база данных — за единицы и десятки миллисекунд, а сложный запрос — за сотни).

Аналогия. Вы готовитесь к экзамену и постоянно заглядываете в одну формулу из учебника. Чтобы не искать её каждый раз, вы выписываете её на стикер и клеите на монитор. Стикер — кеш: быстро, под рукой, но это копия. Если в учебнике исправят формулу, стикер останется со старой версией, пока вы его не перепишете.

Алгоритм, который нужно реализовать в этой работе, называется cache-aside («кеш сбоку»), и состоит из четырёх шагов:

  1. проверить кеш: есть ли в Redis запись с нужным ключом;
  2. если есть (попадание, HIT) — вернуть данные из кеша, база не нужна;
  3. если нет (промах, MISS) — получить данные из базы данных;
  4. сохранить результат в Redis с временем жизни (TTL) и вернуть данные пользователю.
ТерминЧто это простыми словами
ключимя записи в кеше, например tasks:item:5; по ключу данные кладут и достают
HIT / MISSпопадание (данные нашлись в кеше) и промах (данных нет, идём в базу)
TTL (time to live)«срок годности» записи в секундах; по его истечении Redis удаляет запись сам
инвалидацияудаление устаревшей записи из кеша, когда исходные данные изменились
холодный / тёплый кешхолодный — пустой (первые запросы медленные), тёплый — уже заполненный

2. Redis и phpredis

Redis — программа-сервер, как PostgreSQL: приложение подключается к ней по сети (порт 6379 по умолчанию). Это хранилище «ключ — значение». Консоль: docker compose exec redis redis-cli.

Команда RedisЧто делаетМетод phpredis
SET key value EX 60записать значение со временем жизни 60 секунд$redis->setex($key, 60, $value)
GET keyполучить значение (или (nil), если ключа нет)$redis->get($key) (вернёт false, если ключа нет)
DEL keyудалить ключ$redis->del($key)
TTL keyсколько секунд осталось жить ключу (-2 — ключа нет, -1 — живёт вечно)$redis->ttl($key)
INCR keyувеличить число на 1 (создаст ключ, если его нет)$redis->incr($key)
--scan --pattern "taskapp:*"посмотреть ключи по шаблону (в redis-cli, не команда внутри него)$redis->scan($it, $pattern)

Redis хранит строки, а нам нужны массивы. Поэтому при записи массив превращают в строку JSON (json_encode), а при чтении обратно (json_decode($raw, true)).

$redis = new Redis(); $redis->connect('127.0.0.1', 6379, 0.5); // адрес, порт, таймаут подключения в секундах $redis->setOption(Redis::OPT_PREFIX, 'taskapp:'); // ко всем ключам добавится префикс $redis->setex('projects:all', 300, json_encode($projects)); // записали на 5 минут (ключ в Redis: taskapp:projects:all) $raw = $redis->get('projects:all'); // строка JSON или false $projects = $raw === false ? null : json_decode($raw, true);

Префикс ключей. В одном Redis может жить много приложений, поэтому все наши ключи начинаются с taskapp:. Это позволяет, например, очистить кеш приложения, не трогая чужие данные.

3. Что кешировать

Кешировать всё подряд не нужно. Кеш помогает, когда выполняются все условия:

В нашем приложении пять сценариев. Подумайте заранее: какой выиграет больше всех, а какой почти не выиграет?

4. Ключи и время жизни (TTL)

Ключ должен быть уникальным для каждого набора данных и понятным человеку. Договорённость: части названия через двоеточие, от общего к частному.

ДанныеКлючTTLПочему так
список проектовprojects:all300 ссправочник меняется редко; 5 минут — страховка на случай, если инвалидация где-то не сработает
карточка задачиtasks:item:560 сномер задачи входит в ключ: у каждой задачи своя запись
список задачtasks:list:v3:<md5>60 свариантов запроса много, ключ строится из всех параметров (статус, проект, поиск, сортировка, страница)
отчётreport:summary120 сне зависит от параметров, дорогой запрос
номер версии списковtasks:versionбез TTLсчётчик для инвалидации (см. ниже)

Ключ списка с параметрами. Запросов списка бывает бесконечно много (?status=done, ?q=форм, ?project_id=7&sort=title...), и у каждого свой результат. Поэтому все параметры собирают в массив, превращают в строку JSON и берут от неё md5 (короткий «отпечаток» из 32 символов): одинаковые параметры дают одинаковый ключ, разные — разные.

$key = 'tasks:list:v' . Cache::version('tasks:version') . ':' . md5(json_encode([$status, $projectId, $q, $sort, $limit, $offset])); // например: tasks:list:v3:9f2c7a1e5b0d4c8a6e3f1b2d7a9c4e60

TTL как страховка и как компромисс. Чем дольше живёт запись, тем меньше работы у базы и тем выше шанс показать устаревшее. Для данных, которые мы умеем инвалидировать, TTL — страховка (если мы что-то забыли, ошибка исправится сама). Для данных, которые инвалидировать нельзя (например, ответ внешнего сервиса), TTL — единственная защита, и подбирают его по тому, на сколько данные могут «отстать».

5. Инвалидация: самое сложное

Известная шутка: в программировании только две сложные вещи — инвалидация кеша и придумывание имён. Данные изменились, а копия в кеше устарела: пользователь изменил задачу и всё равно видит старое название.

СпособКак работаетГде в нашей работе
по времени (TTL)запись удаляется сама по истечении срокау всех записей: страховка
при изменении данныхпосле INSERT, UPDATE, DELETE сразу удаляем связанные записи (DEL)карточка задачи, список проектов, отчёт
версия набора ключейв имя ключа входит номер версии; при изменении номер увеличивают (INCR), и все старые ключи разом перестают использоватьсясписки задач: вариантов много, перечислить и удалить их все нельзя

Почему для списков нужна версия? Список задач бывает с десятками разных параметров, и в Redis может лежать сотня разных ключей. Какие из них устарели после создания новой задачи? Практически любые. Искать и удалять их по одному долго, поэтому мы просто увеличиваем номер версии: новые запросы ищут ключ с новой версией, не находят (MISS), берут данные из базы и кладут под новым ключом, а старые Redis удалит сам по истечении TTL.

Что изменилосьЧто удалить или обновить
создана, изменена или удалена задачаверсия списков tasks:version (+1), отчёт report:summary, карточка этой задачи tasks:item:N
создан, изменён или удалён проектсписок проектов projects:all, отчёт report:summary (в нём названия проектов)

Проверка: забыли инвалидацию? Автотесты лабораторной работы №9 уже заодно проверяют это: если после «создать задачу» список или карточка отдаются старые, тесты упадут. Попробуйте выполнить задания 3.x и не выполнять 4.x, и вы увидите «залипшие» данные своими глазами.

6. Кеш не должен ронять приложение

Кеш — ускоритель, а не обязательная часть. Если Redis выключен, медленный или недоступен, приложение должно продолжить работать, пусть и медленнее. Для этого:

  • подключение выполняется с коротким таймаутом (0,5 секунды): недоступный Redis не должен «вешать» запрос;
  • любая работа с Redis обёрнута в try/catch (RedisException): при ошибке метод возвращает «нет данных», и приложение идёт в базу;
  • после первой неудачи в этом запросе к Redis больше не обращаемся.

Результат работы кеша виден в заголовке ответа X-Cache: HIT (данные из Redis), MISS (данных не было, взяли из базы и положили в кеш) или BYPASS (кеша нет: выключен или Redis недоступен). Этот заголовок — главный инструмент проверки и отладки.

curl -i http://localhost:8000/api/projects -H "Authorization: Bearer ВАШ_ТОКЕН" HTTP/1.1 200 OK X-Cache: HIT

7. Как правильно измерять

Измерение производительности — это эксперимент, и у него есть правила. Иначе цифры окажутся бесполезными.

ПравилоПочему
сравнивать при одинаковых условиях: одни данные, один сервер, один запросиначе разница будет вызвана не кешем
много запросов, а не одинвремя одного запроса случайно: сетевая «икота», сборщик мусора. Берут среднее и p95
различать холодный и тёплый кешпервый запрос (MISS) медленнее обычного: он и в базу сходил, и в Redis записал. Выигрыш виден на повторных запросах
на больших данныхна семи задачах база отвечает мгновенно, и кеш ничего не ускорит
измерять и скорость одного запроса, и пропускную способностьвремя ответа важно пользователю, а запросов в секунду — серверу при нагрузке
учитывать накладные расходыв каждом запросе есть то, что кеш не ускоряет: запуск PHP, проверка токена. Они составляют «пол» времени ответа
ПоказательЧто означает
среднеесумма времён ÷ число запросов; чувствительно к редким медленным запросам

В заготовке есть скрипт bin/benchmark.php: он сам входит в систему, для каждого сценария делает серию запросов без кеша (с заголовком X-Cache-Mode: off, который обходит кеш) и с кешем (после очистки), затем те же запросы параллельно, и печатает готовую таблицу. Заголовок X-Cache-Mode: off работает только при debug = true в настройках: это режим для измерений.

Критерии проверяются на вашем приложении. При защите нужно уметь показать в браузере и в redis-cli, как данные попадают в кеш и удаляются из него, объяснить выбор ключей и TTL, показать, что происходит после изменения данных, и объяснить результаты измерений: почему у одних сценариев выигрыш большой, а у других почти нет.

Повышенная сложность (по желанию)

  • кеш авторизации: проверка токена при каждом запросе ходит в базу (две выборки). Закешируйте соответствие «токен → участник» на 60 секунд (не забудьте удалять запись при выходе) и измерьте, как изменилось время самых быстрых запросов (карточки задачи);
  • защита от «лавины»: когда популярная запись истекает, много одновременных запросов идут в базу сразу. Реализуйте блокировку: SET lock:ключ 1 NX EX 10 (команда выполнится только у первого запроса), остальные немного ждут и берут готовое из кеша;
  • разброс TTL: добавляйте к времени жизни случайную добавку (например, 0–15%), чтобы записи, созданные одновременно, не истекали одновременно; объясните, зачем;
  • доля попаданий: команда INFO stats показывает keyspace_hits и keyspace_misses; посчитайте hit ratio после нескольких минут работы клиента;
  • HTTP-кеш: добавьте для списка проектов заголовки Cache-Control и ETag (ответ 304, лекция 3.1, раздел 9) и сравните с кешем на сервере: что экономят в каждом случае;
  • ограничение памяти: запустите Redis с параметрами --maxmemory 2mb --maxmemory-policy allkeys-lru, наполните кеш большим числом ключей и объясните, что произойдёт.
