Теоретическая база

1. Как PHP-приложение отвечает на запрос

Когда вы открываете в браузере адрес http://localhost:8000/tasks/5, происходит следующее:

  1. браузер отправляет на сервер HTTP-запрос: метод (GET) и адрес (/tasks/5);
  2. веб-сервер запускает PHP-программу;
  3. программа формирует ответ: код состояния (например, 200 или 404) и содержимое (HTML-страницу);
  4. сервер отправляет ответ браузеру, и работа программы полностью завершается.

Важно запомнить: PHP запускается заново на каждый запрос и «забывает» всё после ответа. Значения переменных между двумя запросами не сохраняются. Поэтому данные, которые должны жить дольше одного запроса (созданные задачи), хранят в файле или базе данных. В нашей работе это файл storage/tasks.json.

2. Единая точка входа и встроенный сервер

В современных приложениях все запросы направляются в один файл public/index.php. Он называется front controller («передний контроллер»). Дальше уже PHP-код решает, что делать с каждым адресом. Так не нужно создавать отдельный файл для каждой страницы.

Запуск встроенного сервера PHP (команды выполняются в терминале в папке lab6/src):

php -S localhost:8000 -t public

Ключ -S запускает сервер на адресе localhost:8000, а -t public говорит, что «наружу» открыта только папка public. Так остальные файлы (модели, данные, настройки) недоступны по прямому адресу, а это защита. Сервер нужно оставить работать в терминале; остановить его можно клавишами Ctrl+C. Каждый запрос он печатает в терминале, а ошибки PHP выводятся и на странице, и в терминале.

Перезапускать сервер после правки кода не нужно: PHP читает файлы заново на каждый запрос, достаточно обновить страницу в браузере.

4. Маршрутизация

Маршрут — это правило «на такой запрос отвечает такой код». Маршрут состоит из метода (GET или POST), шаблона адреса и обработчика: класса-контроллера и его метода. Все маршруты собраны в одной таблице, routes/web.php:

$router->get('/', [HomeController::class, 'index']); $router->get('/tasks', [TaskController::class, 'index']); $router->get('/tasks/{id}', [TaskController::class, 'show']); $router->post('/tasks', [TaskController::class, 'store']);

Читается так: «запрос GET /tasks/5 обрабатывает метод show класса TaskController». Фигурные скобки в {id} означают «здесь может быть любое значение»: оно передаётся в метод как параметр с тем же именем (show(string $id)).

Работа маршрутизатора (класс Router) складывается из четырёх действий:

  1. регистрация: методы get() и post() запоминают маршруты в списке;
  2. поиск: для пришедшего запроса маршруты просматриваются по порядку, берётся первый, у которого совпали метод и адрес;
  3. вызов: создаётся объект контроллера и вызывается нужный метод, ему передаются параметры из адреса;
  4. ошибка: если ни один маршрут не подошёл, возвращается страница 404.

Порядок маршрутов важен. Адрес /tasks/create подходит и к маршруту /tasks/create, и к маршруту /tasks/{id} (слово create сойдёт за значение id). Побеждает тот, что записан раньше. Поэтому конкретные адреса пишут выше шаблонных.

MVC делит приложение на три роли, и у каждой своя папка:

6. Контроллеры

Контроллер — это обычный PHP-класс, в котором каждый метод обрабатывает один запрос (такой метод называют action, «действие»). Внутри он делает три вещи: (1) читает данные запроса, (2) обращается к моделям, (3) показывает шаблон.

// GET /tasks/5 — значение {id} из маршрута приходит в параметр $id public function show(string $id): void { $task = $this->tasks->find((int) $id); // (2) спросили у модели; (int) превращает '5' в число 5 if ($task === null) { notFound(); // задачи нет: страница 404 с кодом ответа 404 } view('tasks/show', ['task' => $task]); // (3) показали шаблон и передали ему данные }

Откуда контроллер берёт данные запроса:

7. Представления: PHP внутри HTML

Шаблон — это HTML-файл, в который вставлены фрагменты PHP. Три конструкции, которые нужны в работе:

<h1><?= e($task['title']) ?></h1> <!-- вывести значение --> <?php foreach ($tasks as $task): ?> <!-- цикл: блок повторится для каждой задачи --> <li><?= e($task['title']) ?></li> <?php endforeach; ?> <?php if (count($tasks) === 0): ?> <!-- условие --> <p>Задач нет.</p> <?php endif; ?>

Безопасность. Любое значение, пришедшее от пользователя, выводится только через функцию e(...). Она заменяет символы <, >, & на безопасные коды. Иначе пользователь может ввести в форму «название» <script>...</script>, и этот скрипт выполнится в браузере каждого, кто откроет страницу (XSS-атака).

Общая «рамка» страниц (шапка и подвал) вынесена в Views/layout/, поэтому в каждом шаблоне пишется только содержимое страницы. Данные в шаблон передаёт функция view('имя_шаблона', ['переменная' => значение]).

8. Формы, коды ответа и перенаправление

Страницы открываются запросом GET, а форма отправляет данные запросом POST. Поэтому для одного адреса /tasks есть два маршрута: GET (показать список) и POST (принять форму). После успешной обработки формы сервер не показывает страницу сам, а перенаправляет браузер на список. Иначе обновление страницы (F5) повторно отправило бы форму и создало дубликат.

10. Как искать ошибки и не наделать их

Правила, которые убирают половину ошибок:

  1. Файл PHP начинается с <?php в самой первой строке: ни пробела, ни пустой строки перед ним (иначе позже появится ошибка «headers already sent»).
  2. Каждая команда заканчивается точкой с запятой ;. Скобки ( ), { }, [ ] и кавычки всегда парные: редактор подсвечивает парную скобку, проверяйте её.
  3. Регистр букв важен: TaskController.php и taskcontroller.php разные файлы, $task и $Task разные переменные. Имя файла с классом совпадает с именем класса.
  4. После изменения сохраните файл (Ctrl+S или Cmd+S) и обновите страницу (F5). Перезапускать сервер не нужно.
  5. Делайте и проверяйте по одному заданию: выполнили TODO → проверили строку «✔ Проверка» в комментарии → только потом следующее. Не пишите сразу всё.
  6. Раскомментируя код из подсказки, убирайте // у всего фрагмента: вместе с закрывающими } и ]);, иначе скобки окажутся непарными.

Как читать сообщение об ошибке. PHP показывает ошибки на странице и в терминале, где запущен сервер. Образец:

Fatal error: Uncaught Error: Call to undefined function view() in /путь/к/проекту/public/index.php on line 7

Call to undefined function view()суть: вызвана функция view(), которой нет. Причина: не подключён файл app/helpers.php или опечатка в имени

Другие частые сообщения того же вида:

СообщениеЧто случилось
Warning: Undefined array key "project_id"обращение к элементу массива, которого нет: опечатка в ключе или в массиве другие данные
Fatal error: Uncaught Error: Unknown named parameter $task_idимя параметра метода контроллера не совпадает с именем в фигурных скобках маршрута
  1. Прочитайте первую строку сообщения (остальное вам пока не нужно).
  2. Найдите в ней файл и номер строки.
  3. Откройте строку и 2–3 строки выше: ошибка часто находится сразу перед указанным местом (например, забыта ;).
  4. Сравните свой код с подсказкой или готовым образцом буква в букву.
  5. Не получилось за 10 минут: позовите преподавателя и покажите текст ошибки.

Если сообщений нет, а страница пустая или результат неверный. В JavaScript вы выводили значения через console.log. В PHP то же самое делает var_dump (покажет значение и его тип). Добавьте в нужное место контроллера строку и обновите страницу:

echo '<pre>'; var_dump($task); echo '</pre>'; exit;

На странице появится содержимое переменной (exit; останавливает программу сразу после вывода, чтобы вы его увидели):

array(3) { 'id' => int(3) 'title' => string(12) "Пример" 'status' => string(3) "new" }

Обязательно удалите эту строку после проверки: иначе страница не будет работать дальше.

Работа выполняется на готовой заготовке по шагам. После каждого шага рекомендуется делать коммит в Git. Все задания помечены в коде словом TODO с номером шага, а после каждого задания в комментарии есть строка «✔ Проверка»: выполните её, прежде чем идти дальше. Задания можно найти так: найти их можно поиском по проекту в VS Code (Ctrl+Shift+F или Cmd+Shift+F). Подсказки в комментариях содержат почти готовый код, но вам нужно разобраться, что он делает: именно по этому будут задавать вопросы при защите.

Ориентировочное время (всего 4 академических часа = 180 минут):

Шаг 0А (необязательный). Установка PHP

Выполняется только если команда php -v не работает или показывает версию ниже 8.2. Если PHP уже установлен, переходите к Шагу 0.

  2. Выполните php -v: должна появиться строка PHP 8.2.xx (или новее).
  3. Выполните php -m и убедитесь, что в списке есть json и mbstring: они понадобятся приложению. В стандартных сборках они включены.

Если возникла ошибка, не тратьте на неё больше 15 минут: запишите текст ошибки и позовите преподавателя. Остальные шаги можно начать, работая в паре.

Шаг 0. Подготовка и запуск

  1. Скопируйте заготовку в каталог lab6/src/ своего репозитория и откройте папку в VS Code.
  2. Откройте терминал в папке lab6/src и запустите сервер: php -S localhost:8000 -t public.
  3. Откройте в браузере http://localhost:8000. Вы должны увидеть текст «Сервер работает. Допишите файл по заданиям TODO 1.1 и 1.2.»
  4. Найдите в проекте все пометки TODO и просмотрите готовые файлы: app/helpers.php, app/Models/TaskRepository.php, app/Views/tasks/index.php. Они будут образцами.

Шаг 1. Создание структуры проекта

Создайте структуру серверной части приложения. Структура в заготовке уже построена по рекомендуемой схеме, а точку входа вам нужно написать самим.

  1. Убедитесь, что в проекте есть все каталоги из рекомендованной схемы: public/, app/Controllers/, app/Models/, app/Views/, routes/, config/. Выясните по описанию в теории, для чего нужен каждый.
  2. TODO 1.1. В public/index.php определите константы с путями к каталогам проекта и подключите готовые файлы автозагрузки и вспомогательных функций.
  3. TODO 1.2. Там же создайте маршрутизатор, подключите таблицу маршрутов и передайте ему запрос. Удалите строку-заглушку с echo.

Проверка: после перезагрузки страницы вы должны увидеть пустую страницу без ошибок. Если вместо неё сообщение об ошибке, прочитайте его: в нём указан файл и строка.

Шаг 2. Реализация маршрутизации

Создайте механизм обработки HTTP-запросов. Необходимо обеспечить: регистрацию маршрутов, обработку различных URL, передачу управления соответствующему контроллеру и обработку ошибок при обращении к несуществующим маршрутам. Сложная часть маршрутизатора (поиск подходящего маршрута и вызов контроллера: метод dispatch()) уже написана и подробно прокомментирована: ваша задача разобраться в ней и дописать недостающее.

  1. Прочитайте метод dispatch() в app/Core/Router.php. По комментариям выпишите в черновик (потом пригодится для отчёта), что происходит на каждой строке цикла: какие маршруты пропускаются, как проверяется адрес, как вызывается контроллер.
  2. TODO 2.1. Допишите метод add(), который запоминает маршрут в списке (регистрация маршрутов).
  3. TODO 2.2. В конце dispatch() добавьте обработку несуществующих маршрутов: страница 404 с кодом ответа 404.
  4. TODO 2.3. В routes/web.php зарегистрируйте семь маршрутов из таблицы (обработка различных URL). Следите за порядком: /tasks/create должен быть выше /tasks/{id}.

Проверка в этом шаге. Контроллеры пока пустые, поэтому для проверки маршрутов временно добавьте в начало каждого метода контроллера строку, например:

echo 'TaskController::show, id = ' . $id;

Откройте /tasks/5: должна появиться эта строка с id = 5. Откройте /nonexistent: должна появиться страница «404 — страница не найдена». Когда убедитесь, что маршруты работают, строки echo удалите, иначе они испортят страницы.

Шаг 3. Создание контроллеров

Разработайте контроллеры для основных пользовательских сценариев: главная страница, список объектов, просмотр объекта, создание объекта. Каждый контроллер содержит методы обработки соответствующих запросов. Должно получиться не менее трёх контроллеров.

Все шаблоны страниц и методы создания объекта (TaskController::create() и store()) уже готовы как образцы: изучите их и используйте как подсказку. Вам остаётся написать методы, которые собирают данные и передают их в шаблон.

  1. TODO 3.1. HomeController::index(): соберите данные для главной (число задач по статусам, число проектов) и передайте их в шаблон home.php.
  2. TODO 3.2. TaskController::index(): список задач с необязательным фильтром ?status=.... Шаблон tasks/index.php изучите заранее.
  3. TODO 3.3. TaskController::show($id): одна задача; если её нет — notFound().
  4. TODO 3.4 и 3.5. ProjectController (методы index и show) напишите самостоятельно по образцу TaskController: так вы убедитесь, что поняли, как устроен контроллер.
  5. Разберите готовый код формы (TaskController::create() и store()): по комментариям объясните, что делает каждый шаг. Откройте /tasks/create, создайте задачу, найдите её в storage/tasks.json.

Проверка: после каждого контроллера открывайте его адрес в браузере и сверяйтесь с результатом. Ошибки PHP выводятся на странице и в терминале.

Занесите результаты в отчёт: для каждой строки укажите код ответа (вкладка Network или curl -i). Проверка выполняется на данных примера («задачи» и «проекты»): после Шага 5 вы повторите её на данных своей предметной области.

Шаг 5. Перенос на свою предметную область

Сейчас у вас работающее приложение на примере «Система управления задачами»: задачи и проекты. Перенесите его на предметную область вашего проекта из лабораторной работы №1: те же страницы и контроллеры, но с вашими сущностями (например, заказы и клиенты, книги и авторы, обращения и сотрудники).

Перед началом: убедитесь, что Шаг 4 пройден и всё работает, и сделайте коммит в Git. Тогда перенос можно безопасно откатить: git checkout . вернёт файлы к последнему коммиту.

Как выполнить перенос без лишних ошибок:

  • переносите только после Шага 4 и коммита в Git (чтобы можно было откатить изменения командой git checkout .);
  • маршрутизатор (app/Core/Router.php), автозагрузку и структуру каталогов менять не нужно: перенос их не касается;
  • меняйте по одному пункту из таблицы и после каждого открывайте страницу: так ошибка всегда будет в последнем изменённом файле;
  • после переноса просмотрите git diff: вы должны понимать, что изменилось в каждом файле.

3. Проверьте результат.

  1. Повторите таблицу из Шага 4 на своих адресах: все строки должны дать те же коды ответа (200, 404, 422, 302).
  2. Откройте старые адреса примера (/tasks, /projects): теперь они должны возвращать 404. Если открываются, перенос не завершён.
  3. Найдите в проекте остатки примера: поиск по всему проекту в VS Code (Ctrl+Shift+F) по словам task, project (регистр не важен) и по русским подписям примера («Задачи», «задач», «Проекты»). Допустимы только упоминания в комментариях-примерах.
  4. Создайте через форму новую запись и убедитесь, что она появилась в списке и в вашем файле данных в storage/.

4. В отчёт (раздел «Предметная область» в README.md): заполненная карточка предметной области и 2–3 предложения: что вы изменили и как проверили результат.

Что должно получиться в результате

В результате выполнения лабораторной работы должны быть подготовлены:

  • структура PHP-проекта;
  • реализованный механизм маршрутизации;
  • не менее трёх контроллеров;
  • корректная обработка основных HTTP-запросов;
  • демонстрация работы серверной части приложения;
  • работающее приложение на данных вашей предметной области (Шаг 5).

Повышенная сложность (по желанию)

  • напишите метод dispatch() маршрутизатора самостоятельно, не подглядывая в готовый, и сравните с исходным;
  • напишите самостоятельно методы create() и store() и шаблоны страниц (закройте готовые файлы и сравните результат с образцом);
  • ответ 405 Method Not Allowed: если для адреса есть маршрут, но с другим методом (например, GET /tasks есть, а PUT /tasks запросили), отвечать 405, а не 404;
  • сообщение об успехе после создания задачи («Задача создана»), которое показывается один раз после перенаправления (подсказка: сессии, session_start() и $_SESSION);
  • удаление задачи: форма с кнопкой «Удалить», маршрут POST /tasks/{id}/delete, метод модели delete();
  • постраничный вывод списка (/tasks?page=2);
  • вынесение общего кода трёх контроллеров в базовый класс Controller;
  • именованные маршруты и функция route('tasks.show', ['id' => 5]) для построения адресов.

Требования к оформлению

Результаты лабораторной работы должны быть оформлены в виде Git-репозитория. Рекомендуется делать отдельный коммит после каждого шага с понятным сообщением (например, «lab6: маршрутизатор»).

Рекомендуемая структура:

lab6/ ├── README.md ├── src/ ├── images/ └── docs/

Файл README.md должен содержать:

  • название лабораторной работы;
  • цель работы;
  • описание структуры проекта;
  • описание механизма маршрутизации;
  • описание реализованных контроллеров;
  • вывод.

При необходимости в репозиторий добавляются:

  • исходный код (src/);
  • изображения структуры проекта или схем (images/);
  • дополнительные материалы (docs/), например, результаты проверки из Шага 4.

При оформлении рекомендуется:

  • использовать язык разметки Markdown;
  • применять заголовки, списки и таблицы;
  • сопровождать основные этапы реализации пояснениями;
  • придерживаться понятной структуры каталогов и файлов.
