Теоретическая база

Основная теория — в лекции 3.2 «Асинхронная обработка и фоновые задачи». Здесь самое необходимое для работы.

1. Синхронная и асинхронная обработка

В синхронной обработке сервер выполняет всё внутри запроса и отвечает, только когда закончил. Если уведомление отправляется 2 секунды, пользователь ждёт эти 2 секунды. В асинхронной обработке сервер записывает «надо отправить уведомление» в очередь и отвечает сразу, а отправляет его другой процесс.

Аналогия. Кассир в кафе принимает заказ, пробивает чек с номером и сразу переходит к следующему гостю. Кухня готовит заказы по очереди. Гость не стоит у плиты и не мешает остальным; когда заказ готов, ему сообщают. Чек с номером — это номер задачи, кухня — воркер, список чеков — очередь.

ТерминЧто это простыми словами
задача (сообщение)описание работы: что сделать и с какими данными; например, «отправь уведомление о задаче №2»
очередьсписок задач, которые ждут выполнения; кто первым пришёл, того первым и обслужат
производитель (producer)тот, кто ставит задачи в очередь; у нас это обработчик HTTP-запроса
воркер (worker)отдельная программа, которая берёт задачи из очереди и выполняет; работает независимо от веб-сервера
подтверждение (ack)сообщение очереди «задача выполнена, можно забыть»
повтор (retry)новая попытка, если задача не выполнилась
«мёртвая» очередь (dead letter)склад задач, которые не получилось выполнить за все попытки: их разбирает человек
идемпотентностьсвойство операции: повторное выполнение даёт тот же результат, что и первое (не создаёт дубль)

2. Что выносить в фон, а что нет

В фон выносят то, что долгое, может сломаться из-за внешнего сервиса или не обязано быть готово к моменту ответа.

ОперацияВ фон?Почему

3. Redis как очередь

Redis уже работает у вас как кеш. Тот же Redis можно использовать как очередь: в нём есть списки (упорядоченные наборы строк). Задача — это JSON-строка, а очередь — список таких строк.

Команда RedisЧто делаетМетод phpredis
LPUSH key valueположить значение в начало (слева) списка$redis->lPush($key, $value)
BLMOVE src dst RIGHT LEFT 2переложить значение из конца списка src в начало списка dst одной неделимой командой; если src пуст, ждать до 2 секунд (B — blocking)$redis->blmove($src, $dst, 'RIGHT', 'LEFT', 2) (вернёт false, если не дождались)
LREM key 1 valueудалить одно вхождение значения из списка$redis->lRem($key, $value, 1)
LLEN keyсколько элементов в списке$redis->lLen($key)
LRANGE key 0 -1показать все элементы списка (для просмотра)$redis->lRange($key, 0, -1)
ZADD key 1730000000 valueположить значение в упорядоченное множество с числом-оценкой (мы кладём время повтора)$redis->zAdd($key, $time, $value)

Как задачи идут по порядку. Новая задача кладётся слева (LPUSH), а берётся справа: так первой берётся самая старая, как в очереди в магазине.

LPUSH queue:default "задача A" # очередь: [A] LPUSH queue:default "задача B" # очередь: [B, A] BLMOVE queue:default queue:default:processing RIGHT LEFT 2 # берём справа: A. Очередь: [B], «в работе»: [A]

Почему не просто «достать» (RPOP)? Если воркер достанет задачу и упадёт, не успев выполнить, задача пропадёт навсегда. Поэтому задачу не достают, а перекладывают из очереди в список «в работе» (BLMOVE), а после успешного выполнения удаляют оттуда (LREM, это и есть подтверждение, ack). Если воркер упал, задача осталась на виду в списке «в работе», и её можно вернуть в очередь.

4. Устройство очереди в приложении

Очередь состоит из четырёх ключей Redis (все начинаются с префикса taskapp:):

КлючТипЧто хранит
queue:defaultсписокожидающие задачи
queue:default:processingсписокзадачи «в работе»: воркер взял, но ещё не подтвердил
queue:default:delayedупорядоченное множествозадачи, которые будут повторены позже (оценка — время, когда их пора вернуть в очередь)
queue:default:deadсписок«мёртвая» очередь: задачи, не выполненные за все попытки

Задача — JSON-строка. Кладите в неё только нужное для обработки (номера и тексты), а не целые записи из базы: к моменту выполнения запись может измениться, а очередь не должна раздуваться.

{ "id": "a1b2c3d4e5f60718", // номер задачи (16 случайных символов) "type": "notification", // тип: по нему воркер выбирает, какой код запустить "payload": {"task_id": 2, "title": "Подключить форму", "new_status": "done", ...}, "attempts": 0, // сколько раз уже не получилось "created_at": "2026-11-09T12:00:00+00:00" }

Путь задачи: обработчик запроса Jobs::dispatch() → Queue::push кладёт в queue:default → воркер Queue::reserve перекладывает в processing → Jobs::run выполняет → Queue::ack убирает из processing. Если выполнить не удалось, Queue::fail кладёт задачу в delayed (повтор) или dead (отказ).

5. Воркер

Воркер — обычный PHP-скрипт с бесконечным циклом. Он не связан с веб-сервером: запускается в отдельном окне терминала, его можно остановить и запустить заново, а можно запустить несколько копий (задачи между ними не дублируются, потому что BLMOVE отдаёт задачу только одному).

while ($running) { Queue::promote($queue); // вернуть в очередь задачи, у которых прошла пауза перед повтором $reserved = Queue::reserve($queue, 2); // взять задачу (ждать не дольше 2 секунд) if ($reserved === null) { continue; } // задач нет: проверить флаг остановки и ждать дальше [$job, $raw] = $reserved; try { Jobs::run($job); // выполнить Queue::ack($raw, $queue); // подтвердить } catch (Throwable $e) { Queue::fail($job, $raw, $e->getMessage(), $queue); // ошибка: повторить позже или отказаться } }

Обработчик задачи. Тип задачи связан с классом: notification → NotificationJob, report → ReportJob (реестр Jobs::handlers()). У класса один метод handle($payload, $jobId, $attempt): он получает данные и выполняет работу. Если он бросает исключение, задача считается невыполненной.

Остановка воркера. Нажатие Ctrl+C посылает процессу сигнал. Если его не перехватить, процесс умрёт посреди задачи. Правильно: поймать сигнал, поставить флаг $running = false, доделать текущую задачу и выйти (задание 3.4). В рабочих системах воркером управляют Supervisor или systemd: они перезапускают упавший воркер и запускают нужное число копий.

6. Надёжность: повторы, «мёртвая» очередь, идемпотентность

Что случилосьЧто делает система
обработчик бросил исключение (внешний сервис не ответил, ошибка в данных)повтор: задача уходит в delayed с паузой 2, 4, 8 секунд (пауза растёт: сломавшемуся сервису нужно время прийти в себя); после трёх неудач — в dead
воркер убили посреди работы (kill -9, отключилось питание)задача осталась в processing; при следующем запуске воркер возвращает её в очередь (Queue::recover)
воркер остановили Ctrl+Cтекущая задача доделывается, затем воркер выходит
Redis недоступен в момент постановкизадача потеряна: Jobs::dispatch вернёт null. Для уведомления это терпимо, для денег нет (в рабочих системах используют схему outbox: задачу сначала пишут в базу в той же транзакции)

Очередь даёт гарантию «как минимум один раз» (at-least-once): задача выполнится хотя бы раз, но после сбоя может выполниться дважды (воркер успел записать результат, но не успел подтвердить). Поэтому обработчик должен быть идемпотентным. В нашем уведомлении это сделано на уровне базы: в таблице notifications пара (job_id, user_id) уникальна, а запись идёт командой INSERT ... ON CONFLICT (job_id, user_id) DO NOTHING: повтор той же задачи не создаёт второго уведомления.

7. Как отвечать пользователю

Для операции, которая выполняется в фоне, у клиента два вопроса: «принято?» и «готово ли?». Для этого:

  • быстрые операции с побочным эффектом (уведомление) просто отвечают как раньше, а в заголовок X-Job-Id кладут номер задачи;
  • операции с результатом, который клиент потом заберёт (отчёт), отвечают кодом 202 Accepted («запрос принят, но ещё не выполнен») и заголовком Location с адресом, где смотреть состояние. Клиент периодически спрашивает этот адрес: queued (ждёт) → processing (выполняется) → done (готово) или failed (не вышло, причина в поле error).
POST /api/reports → 202 Accepted, Location: /api/reports/1, {"id": 1, "status": "queued"} GET /api/reports/1 → {"status": "processing"} ... позже ... {"status": "done", "rows_count": 7} GET /api/reports/1/download → CSV-файл (пока не готов: 409 Conflict)

Режим «без очереди». Чтобы увидеть, что дала очередь, в приложении есть переключатель: заголовок запроса X-Queue-Mode: sync (работает при debug = true) просит сервер выполнить задачу прямо в запросе, как было бы без очереди.

Повышенная сложность (по желанию)

  • несколько очередей: долгие задачи (отчёты) ставьте в очередь reports, быстрые (уведомления) в default, и запустите по воркеру на каждую (php bin/worker.php --queue=reports); объясните, какую проблему это решает (быстрое уведомление не ждёт долгий отчёт);
  • несколько воркеров: запустите два воркера и поставьте 10 демо-задач (php bin/queue-demo.php 10); сравните общее время и объясните, почему задачи не выполнились дважды;
  • срок выполнения: научите recover возвращать только те задачи, которые лежат в «в работе» дольше заданного срока (запоминайте время взятия), чтобы запуск второго воркера не забирал задачу у первого;
  • outbox: вместо постановки в Redis прямо из запроса записывайте задачу в таблицу outbox той же транзакцией, что и изменение задачи; отдельный процесс пересылает записи в Redis. Объясните, какую проблему решает эта схема;
  • приоритеты и расписание: задачи с высоким приоритетом выполняются раньше; задача, поставленная «на 10:00»;
  • Supervisor или Docker: запустите воркер как отдельный контейнер в docker-compose.yml с автоматическим перезапуском;
  • метрики: эндпоинт GET /api/queue/stats для руководителя: размеры очереди, число «мёртвых» задач, время самой старой задачи.
