# Полнотекстовый поиск по задачам: устройство и обоснование

## 1. Что и зачем ищем

Объект поиска — задача. В документ индекса кладётся название задачи, описание, статус, приоритет, срок и **название проекта** (проекты отдельно не индексируются: задачу можно найти по проекту, не делая второй индекс). Поиск нужен там, где пользователь вводит слова, а не номер или точное значение.

| Требование пользователя | `ILIKE '%текст%'` | OpenSearch |
|-------------------------|-------------------|------------|
| «форма» находит «форму» | нет | да (анализатор `russian`) |
| порядок слов не важен | нет | да |
| опечатка | нет | да (`fuzziness`) |
| поиск по описанию и проекту | нужен отдельный запрос по каждому полю | один запрос по нескольким полям |
| лучшее — первым | нет | да (оценка релевантности) |
| подсветка найденного | нет | да |

## 2. Структура индекса

```json
{
  "settings": { "number_of_shards": 1, "number_of_replicas": 0 },
  "mappings": { "properties": {
    "id":            { "type": "integer" },
    "title":         { "type": "text", "analyzer": "russian", "fields": { "raw": { "type": "keyword", "ignore_above": 256 } } },
    "description":   { "type": "text", "analyzer": "russian" },
    "project_title": { "type": "text", "analyzer": "russian" },
    "project_id":    { "type": "integer" },
    "status":        { "type": "keyword" },
    "priority":      { "type": "keyword" },
    "due_date":      { "type": "date", "format": "yyyy-MM-dd" },
    "created_at":    { "type": "date" }
  } }
}
```

| Решение | Почему |
|---------|--------|
| `text` + `russian` для названия, описания, проекта | текст разбирается на слова, слова сводятся к основе («форма», «формы», «формой» → «форм»), служебные слова («и», «в», «на») отбрасываются |
| `keyword` для `status` и `priority` | значение сравнивается целиком; по нему фильтруют и (в повышенной сложности) группируют. Если сделать `text`, фильтр `term` по значению `in_progress` ничего не найдёт: анализатор разберёт слово иначе |
| `title.raw` (keyword) | строка целиком нужна для сортировки по названию: по `text`-полю сортировать нельзя |
| `integer` для `id`, `project_id` | числовые сравнения и фильтры; по `id` упорядочиваются результаты с одинаковой оценкой |
| 1 осколок, 0 копий | узел один, данных мало: больше осколков и копий только замедлили бы работу |
| структуру нельзя изменить у готового индекса | чтобы изменить mapping, создают новый индекс и переключают псевдоним (см. раздел 3) |

Анализатор можно проверить: `POST /tasks/_analyze` с телом `{"analyzer": "russian", "text": "форма формы формой"}` вернёт три раза одно слово.

## 3. Индексация

### 3.1. Полная переиндексация (`bin/reindex.php`, `Search::reindexAll`)

1. Создаётся новый индекс `tasks_v<время>` с нашей структурой. Название не повторяется, поэтому два запуска не мешают друг другу.
2. Автоматическое обновление индекса (`refresh_interval`) отключается: при загрузке оно только мешает.
3. Задачи читаются из PostgreSQL пачками по 500 с условием `id > последний`, что работает быстро и не зависит от размера таблицы, и загружаются запросом `_bulk`. Тело запроса — строки NDJSON (на документ две: «что сделать» и сам документ), в конце обязательно перевод строки. После ответа проверяется поле `errors`: `_bulk` отвечает кодом 200 даже тогда, когда часть документов отвергнута.
4. Обновление индекса включается обратно (`1s`), делается `_refresh`: загруженное становится видимым.
5. Псевдоним `tasks` переключается на новый индекс **одной операцией** `_aliases` (убрать у старого, добавить новому): поиск ни на мгновение не остаётся без данных.
6. Удаляются старые индексы (и «осиротевшие» после прошлых сбоев).

Если на любом шаге ошибка, недостроенный индекс удаляется, а псевдоним продолжает указывать на прежний работающий индекс.

### 3.2. Синхронизация при изменениях (`search_index`)

| Событие | Что кладём в очередь | Что делает воркер |
|---------|---------------------|-------------------|
| задачу создали или изменили | `{"task_id": N}` | берёт задачу из PostgreSQL и кладёт документ в индекс (`PUT /tasks/_doc/N`; документ с таким номером заменяется) |
| задачу удалили | `{"task_id": N}` | задачи в PostgreSQL нет, значит удаляет документ (`DELETE`; 404 не ошибка) |
| проект переименовали | `{"project_id": P}` | берёт все задачи проекта и обновляет их документы одним `_bulk` (название проекта хранится в каждом документе) |

**Почему в очереди «что проверить», а не «что изменилось».** Если положить в задачу сами данные, то при двух быстрых изменениях и повторной доставке индекс может получить старую версию позже новой. Если положить только номер, воркер всегда читает **текущее** состояние базы: порядок задач не важен, повтор не вредит (идемпотентность), а при гонке выигрывает свежая версия. Цена: лишнее чтение из PostgreSQL.

**Почему через очередь.** Обращение к OpenSearch — сетевой вызов, который может быть медленным или завершиться ошибкой. Если выполнять его в запросе пользователя, сбой поискового сервера превратится в сбой сохранения задачи. Через очередь ответ приходит сразу, а при ошибке воркер повторит попытку (лабораторная работа №11).

**Параметры.** `refresh=wait_for` на одиночных операциях: воркер завершает задачу, когда документ стал виден поиску (поэтому «search_index: готово» занимает около секунды). Для массовых операций так делать нельзя, им достаточно общего `_refresh`. `require_alias=true`: если псевдонима нет, запрос завершается ошибкой, а не молча создаёт индекс `tasks` со случайной структурой (после этого нельзя было бы создать псевдоним с тем же именем).

### 3.3. Что может пойти не так

| Что случилось | Что с копией | Как исправить |
|---------------|--------------|---------------|
| воркер выключен | копия отстаёт, задачи копятся в очереди | запустить воркер: он догонит |
| Redis недоступен в момент постановки | задача `search_index` потеряна, копия разошлась с базой | `php bin/reindex.php` |
| OpenSearch недоступен | задача `search_index` повторяется три раза с паузами 2 и 4 секунды, затем попадает в «мёртвую» очередь | запустить OpenSearch, затем `php bin/reindex.php` (или вернуть «мёртвые» задачи) |
| индекса ещё нет | `require_alias` отвергает запись, задача уходит в повторы | `php bin/reindex.php` |
| изменили структуру индекса | старый индекс остаётся со старой структурой | `php bin/reindex.php` (создаст новый индекс с новой структурой) |
| `reset-db.php` | база вернулась к 7 задачам, индекс надо вернуть тоже | скрипт перестраивает индекс сам (если OpenSearch доступен) |

Вывод: копию в OpenSearch можно в любой момент безболезненно пересоздать из PostgreSQL, и этим пользуются для лечения любых расхождений.

## 4. Поиск

### 4.1. Запрос

- `multi_match` по полям `title^3`, `project_title^2`, `description`: слова ищутся во всех трёх, при этом совпадение в названии в три раза важнее, чем в описании.
- По умолчанию достаточно совпадения **любого** слова запроса (оператор «или»): чем больше слов совпало и чем они реже встречаются в данных, тем выше оценка. Поэтому запрос «сверстать подключить написать» находит три задачи, а «срочный договор для партнёров» на большой базе находит тысячи (где совпало хотя бы одно слово), но самые подходящие идут первыми. Если нужно строго «все слова», используют оператор `and` или `minimum_should_match` (повышенная сложность).
- `fuzziness: AUTO`: допускается 0 ошибок в слове из 1–2 букв, 1 ошибка в слове из 3–5, 2 ошибки в более длинном. Слово сначала проходит анализатор, и нечёткость применяется к основе. Риск: слишком много результатов для коротких слов.
- Фильтры (`status`, `project_id`) лежат в `bool.filter`: они только отсеивают и не меняют оценку, а OpenSearch кеширует их результаты.
- Страницы: `from` и `size` (в API `offset` и `limit`, не больше 100). Для очень глубоких страниц `from` неэффективен (`search_after`), но для учебной работы достаточно.
- `track_total_hits`: считать точное число найденных (по умолчанию OpenSearch считает только до 10 000).
- Сортировка: `_score` по убыванию, затем `id` по возрастанию (чтобы порядок равных результатов не менялся от запроса к запросу).

### 4.2. Релевантность

Оценка (`_score`) считается алгоритмом BM25: редкое слово ценнее частого; слово, встречающееся в документе чаще, повышает оценку, но с затуханием; в коротком поле (название) совпадение весомее, чем в длинном (описание). Вес поля умножает оценку этого поля. Автотест проверяет, что задача, где слово «квартальный» стоит в названии, идёт выше задачи, где оно в описании.

### 4.3. Подсветка и безопасность

Подсветка оборачивает найденные слова в `<mark>`. Результат выводится на страницу как HTML, поэтому с `encoder: html` OpenSearch заменяет `<`, `>` и `&` в самом тексте на безопасные коды, оставляя настоящими только свои теги. Без этого название «`<script>alert(1)</script>`» исполнилось бы в браузере (XSS). Клиент использует подсвеченное значение через `innerHTML`, а если подсветки нет (запасной поиск, поле без совпадений) — экранирует текст сам.

### 4.4. Запасной поиск

Поиск — удобство, а не основа системы. Если `Search::request` не может подключиться (исключение с кодом 503), `SearchApiController` выполняет `ILIKE` по названию в PostgreSQL. Ответ того же вида; поле `engine` и заголовок `X-Search-Engine` сообщают, что искал PostgreSQL. Другие ошибки (код 502 от OpenSearch, ошибка в коде) пробрасываются дальше: иначе запасной вариант скрыл бы поломку.

### 4.5. Права доступа

В индекс попадают все задачи. В нашей системе все участники видят все задачи, поэтому фильтр доступа не нужен. Если бы у задач были права (например, «только свой проект»), фильтр по доступу пришлось бы добавлять в **каждый** поисковый запрос (или хранить права в документе): поисковый сервер сам о правах не знает. В рабочих системах это частый источник утечек.

### 4.6. Журнал поиска и личные данные

Каждый запрос — событие `search` (лабораторная работа №12): `q`, `found`, `took_ms`, `engine`. Запросы с `found = 0` показывают, что люди ищут, но не находят. Запросы могут содержать личные данные, поэтому длинные запросы обрезаются (200 символов), а читает журнал только руководитель.

## 5. Сравнение с `ILIKE`

Методика: `bin/search-compare.php` для каждого запроса делает один прогревочный и 20 замеряемых вызовов подряд и печатает медиану (одно случайно медленное выполнение не портит результат). PostgreSQL: тот же запасной поиск, что в приложении (`TaskRepository::list` с `ILIKE` по названию и подсчётом всех найденных). OpenSearch: `Search::search` целиком (запрос, подсветка, передача по сети).

Результаты на 20 007 задачах (стенд: Docker 4 ГБ, 2 процессора, на нём работали другие контейнеры, OpenSearch с кучей 128 МБ; на 100 000 задач этот стенд начинал подвисать):

| Запрос | `ILIKE`: найдено | `ILIKE`, мс | OpenSearch: найдено | OpenSearch, мс |
|--------|-----------------:|------------:|--------------------:|---------------:|
| отчёт | 987 | 31 | 987 | 17 |
| квартальный отчёт | 56 | 80 | 2123 | 138 |
| квартальные отчёты | 0 | 51 | 2123 | 97 |
| срочный договор для партнёров | 4 | 56 | 4666 | 123 |
| заказчика | 0 | 47 | 2028 | 42 |
| Альфа | 0 | 37 | 1958 | 13 |

Выводы:

1. **Явного выигрыша по времени нет.** `ILIKE` по одному полю на 20 тысячах строк отвечает за десятки миллисекунд. OpenSearch быстрее для простых запросов и там, где `ILIKE` вынужден просматривать таблицу без пользы (слово из проекта: 37 мс против 13), медленнее для запросов из нескольких слов, потому что оценивает тысячи подходящих документов.
2. **Выигрыш в качестве.** «квартальные отчёты» (другая форма слова), «заказчика» (слово из описания), «Альфа» (слово из проекта): `ILIKE` не находит ничего, OpenSearch находит тысячи.
3. **Больше результатов не значит лучше.** Для «срочный договор для партнёров» найдено 4666: критерий «любое слово». Полезность обеспечивает порядок по релевантности, а не число.
4. **Цифры нестабильны.** Стенд был нагружен другими процессами; повторные запуски давали отличия в разы. Верить стоит порядкам величин и тенденциям, а не отдельным числам.
5. Время индексации: около 1700 задач в секунду на этом стенде.

Когда отдельный поисковый сервер не нужен: если искать надо в одной-двух текстовых колонках до сотен тысяч строк, PostgreSQL сам умеет полнотекстовый поиск (`to_tsvector('russian', ...)`, GIN-индекс, словоформы, ранжирование `ts_rank`) без копии данных и без проблемы согласованности. OpenSearch оправдан, когда нужны нечёткий поиск, сложное ранжирование, подсветка, агрегации и нагрузка, с которой PostgreSQL не справляется (повышенная сложность: сравнить оба).

## 6. Проверка

- Подключение: `php bin/search-check.php`; индекс: `curl localhost:9200/tasks/_mapping?pretty`, `_count`, `_doc/<номер>`.
- Поиск из консоли: `php bin/search-demo.php "форма"` (оценки и подсветка).
- Сравнение: `php bin/search-compare.php`; данные для скорости: `php bin/load-searchdata.php 20000` и `php bin/reindex.php`.
- Автотесты: `php tests/api-tests.php`, разделы 18–21 (55 проверок).
