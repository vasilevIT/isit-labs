# Комплексное тестирование

Тестирование проводилось на трёх уровнях: автоматические тесты API (сервер), сквозные сценарии в браузере (клиент вместе с сервером) и проверки безопасности. Сервер: PHP 8.2, `php -S localhost:8000 -t public`; база данных: PostgreSQL 16 в Docker; браузер: Google Chrome. Скриншоты — в папке `images/`.

## Подготовка

Перед каждым прогоном данные возвращаются к исходным, чтобы результаты не зависели от прошлых экспериментов:

```bash
cd lab9/src
docker compose up -d               # PostgreSQL (один раз)
php bin/reset-db.php               # таблицы создаются заново, данные и токены сбрасываются
php -S localhost:8000 -t public    # в другом окне терминала
```

```bash
php tests/api-tests.php            # код завершения 0 — все проверки прошли
```

## 3. Проверки безопасности

| Проверка | Как проверялась | Результат |
|----------|-----------------|-----------|
| Пароли не хранятся открытым текстом | `SELECT ... FROM users` в psql: в таблице только `password_hash` (bcrypt, начинается с `$2y$`) | пройдена |
| Токен не хранится на сервере | `SELECT ... FROM auth_tokens`: хеш токена (SHA-256), номер участника, срок | пройдена |
| SQL-инъекция в поиске не срабатывает | автотест: запрос `?q=' OR 1=1 --` возвращает 200 и пустой список (значения передаются подготовленными запросами) | пройдена |
| Хеш пароля не уходит клиенту | автотесты: нет слов `password_hash` и `$2y$` в ответах входа, `/api/auth/me`, `/api/users` | пройдена |
| Не раскрывается, существует ли почта | одинаковое сообщение «Неверный email или пароль» для неверной почты и пароля | пройдена |
| Защита API на сервере, а не в интерфейсе | прямые запросы без токена (401) и с токеном разработчика (403), в обход кнопок | пройдена |
| Токен нельзя использовать после выхода и по истечении срока | автотесты, раздел 6; сценарий A4 | пройдена |
| Данные пользователя не вставляются в HTML как код | сценарий C4 | пройдена |

## 4. Что пришлось согласовать между клиентом и сервером

Клиент написан в лабораторной работе №5 под учебный сервер в браузере, API — в лабораторной работе №7. При первом соединении расхождений оказалось больше, чем ожидалось; каждое найдено по вкладке Network и сообщениям клиента.

| Что не совпадало | Как проявлялось | Решение |
|------------------|-----------------|---------|
| Сервер требует `project_id`, в форме проекта нет | при создании задачи ответ 422 | в форму добавлен список проектов, номер отправляется числом |
| Имя поля: клиент `dueDate`, сервер `due_date` | в столбце «Срок» везде «—», срок при создании терялся | клиент использует `due_date` |
| Пустая дата: клиент отправлял `""`, сервер ждёт дату или `null` | 422 «Дата в формате ГГГГ-ММ-ДД» | клиент отправляет `null` |
| Формат ошибок: клиент ждал `fields`, сервер присылает `errors` | пользователь видел только общий текст | `error.fields = data.errors`, сообщения показываются под полями |
| Сортировка: клиент просил `_sort=id&_order=desc`, сервер понимает `sort=-id` | новые задачи оказывались внизу | клиент отправляет `sort=-id` |
| Поиск: клиент отправляет `q`, сервер его не знал | поле поиска ничего не фильтровало | сервер: в SQL `title ILIKE :q` (без учёта регистра, спецсимволы экранируются) |
| Специальные символы в поиске | текст с `&` или `#` обрывал адрес: сервер получал не то, что ввёл пользователь | значения фильтров оборачиваются в `encodeURIComponent` |
| Ответ 401 в середине работы | над пустой таблицей красное «Требуется авторизация», пользователь остаётся на экране списка | клиент возвращает к форме входа с сообщением «Сессия истекла» |
| Ответ 403 для не-руководителя | кнопка «Удалить» вела к ошибке | кнопка показывается только руководителю; сервер запрещает в любом случае |
| Другой адрес клиента (CORS) | «Нет связи с сервером», хотя сервер работает; в консоли `blocked by CORS policy` | адрес клиента добавлен в `cors_origins` на сервере |
